Как сделать перевод точным, устойчивым и проверяемым

Проблема качества находится не только в модели или промпте. Текущий pipeline контролирует форму JSON, но слабо контролирует язык, смысл и педагогическую полезность значений. Ниже — единая карта дефектов и план перехода к измеримому quality pipeline.

Главный вывод. Смена модели необходима, но недостаточна. Надёжное решение состоит из пяти элементов: корректный контракт, детерминированные проверки, model routing, evaluation dataset и сохранение полного learning context.

As-is

Текущий путь запроса

Шаг 1 Telegram input Очистка текста, context hint, классификация.
Шаг 2 Language direction Определение source и target languages.
Шаг 3 · риск Dictionary lookup Точное совпадение; используется первая запись.
Шаг 4 · риск Prompt + schema Один сложный многоязычный structured request.
Шаг 5 · риск AI model Фактическая модель задаётся через system settings.
Шаг 6 · риск Validation Структура проверяется, язык почти нет.
Шаг 7 · риск Render / Save Часть source-level metadata теряется.

Что уже сделано хорошо

  • Structured output через динамическую Zod-схему.
  • Разделение core translation и AI adapter.
  • Dictionary context внедряется через dependency injection.
  • Есть retry с диагностикой ошибок.
  • Есть template-aware отключение лишних полей.

Где теряется контроль

  • Schema подтверждает тип строки, но не её язык и смысл.
  • Prompt содержит противоречивые педагогические требования.
  • Validation не знает назначение каждого поля.
  • Storage contract беднее runtime contract.
  • Нет воспроизводимого quality benchmark.

Problem map

Наблюдаемые дефекты

P-01 · Неверное native-поле

Романизация или дубликат в скобках

Для русского target модель вынуждена «переводить русский на русский» и возвращает романизацию. Для чешского она может просто скопировать target.

Schema требует непустую строку, но не проверяет язык и равенство native === target.
P-02 · Бесполезные примеры

В примерах нет phase out

Target-примеры демонстрируют переводы, а source-примеры находятся в sourceUsage. После сохранения sourceUsage теряется и не отображается во flashcard/dictionary/SRS.

Дополнительно headword validation отключается для любого выражения с пробелом.
P-03 · Семантика полей

Пояснение появляется только иногда

connotationWarning по дизайну должен быть редким предупреждением, но используется как универсальная заметка об употреблении.

Требуются два поля: постоянный usageNote и редкий connotationWarning.
P-04 · Неверный язык

Notes приходят на target language

Prompt просит родной язык пользователя, но runtime не проверяет язык nativeMeaning, native, sourceUsage.explanation и connotationWarning.

validateLanguage() — полный no-op.
P-05 · Sense selection

Для многозначного слова берётся первая запись

Нет нормализации регистра и Unicode, lemmatization, POS/context ranking и явного выбора значения.

Первый database result становится «authoritative context».
P-06 · Нет измерения качества

Улучшение оценивается визуально

Нельзя доказать, что новая модель или prompt снизили число ошибок, потому что нет versioned dataset и стабильных метрик.

Нужны regression fixtures и benchmark по языковым парам.

Contract redesign

Разделить данные по их назначению

Сейчас

{
  nativeMeaning,
  sourceUsage,
  translations: {
    cs: {
      text,
      examples: [{ target, native }],
      connotationWarning
    }
  }
}
→

Предлагается

{
  source: {
    meaningInNative,
    usage: {
      explanationInNative,
      synonymsInSource,
      examplesInSource
    }
  },
  translations: {
    cs: {
      text,
      usageNoteInNative,
      examples: [{
        target,
        native: string | null
      }],
      connotationWarningInNative
    }
  }
}

source.usage

Объясняет исходное изучаемое выражение. Должно сохраняться один раз на vocabulary entry и отображаться во всех learning views.

usageNoteInNative

Регулярное пояснение конкретного target translation: оттенок, регистр, управление и типичный контекст.

connotationWarningInNative

Только редкий риск: оскорбительность, двусмысленность, ложный друг или нежелательный регистр. Поле остаётся optional.

Критическое правило. Для target language, равного native language пользователя, поле example.native должно быть null или отсутствовать. Перевод предложения на тот же язык не запрашивается.

Quality gates

Многоуровневая валидация вместо одного language detector

Уровень 1 — детерминированный

  • Schema и required language keys.
  • native !== target.
  • Script compatibility: Cyrillic, Latin, Han и т. д.
  • Детектор русской романизации в латинице.
  • Запрет IPA/transliteration markers во всех полях.
  • Проверка дублирования notes между языками.

Уровень 2 — лексический

  • Phrase-aware match первого примера.
  • Inflection-aware match для Czech/Russian.
  • Привязка example 1 к main translation.
  • Привязка example 2–3 к указанной alternative/synonym.
  • Проверка отсутствия исходного context hint в переводе.

Уровень 3 — language confidence

  • Language detector только для достаточно длинных строк.
  • Script heuristics для коротких полей.
  • Allowlist исключений для близких языков.
  • Низкая уверенность не блокирует, а отправляет на следующий уровень.

Уровень 4 — semantic judge

  • Только high-risk requests.
  • Модель другого семейства, чтобы снизить correlated errors.
  • Оценивает meaning, naturalness, register и field language.
  • При ошибке — targeted repair, не полный повтор запроса.

Решение validation pipeline

1 Generate Structured response.
2 Deterministic checks Быстро и бесплатно.
3 Risk score Phrase, miss, rare pair.
4 Judge / repair Только при необходимости.
5 Accept + persist С quality metadata.

Model strategy

Сценарий Рекомендуемый класс Причина Политика
Простое слово, dictionary hit Стабильная Flash/Lite Короткий контракт, авторитетный sense. Один request + deterministic validation.
Phrasal verb / phrase Stable mid-tier Нужны naturalness, register и phrase handling. Повышенный risk score.

Context enrichment

Улучшить выбор dictionary sense

Проблема текущего lookup

  1. Точное сравнение исходной строки.
  2. База возвращает несколько entries.
  3. Adapter берёт только первый result.
  4. Он объявляется authoritative context.

Новый pipeline

  1. Unicode normalization + lowercase + trim.
  2. Lookup exact form, lemma и fixed expression.
  3. Собрать candidate senses.
  4. Ранжировать по context hint и POS.
  5. Передать 1–2 лучших sense с confidence.
Не передавать все senses без отбора. Это увеличит prompt и снова повысит неоднозначность. Нужен отдельный sense selection step с ограниченным результатом.

Measurement

Создать evaluation dataset и quality dashboard

Состав dataset: 200–500 кейсов

  • Phrasal verbs и fixed expressions.
  • Идиомы и культурные эквиваленты.
  • Многозначные слова с context hint.
  • Czech/Russian inflection.
  • False friends и register traps.
  • Target = native edge cases.
  • Разные письменности и transliteration leakage.
  • Реальные пользовательские жалобы.

Что хранит один fixture

  • Input, source, targets, native и context.
  • Допустимые основные переводы.
  • Запрещённые ответы и известные failure patterns.
  • Ожидаемый язык каждого поля.
  • Лексема/вариант, который обязан быть в примере.
  • Ожидаемое наличие usage note и warning.

Verified reuse

Кэшировать только проверенные результаты

Почему обычный cache опасен

Если автоматически сохранить любой AI output, случайная ошибка становится постоянной и начинает воспроизводиться без участия validator.

  • Ошибки переживают смену модели.
  • Исправленный prompt не влияет на старую запись.
  • Разные senses могут столкнуться по одному original.

Versioned cache key

{
  normalizedInput,
  sourceLang,
  sortedTargetLangs,
  nativeLang,
  inputType,
  contextHash,
  selectedSenseId,
  outputConfigHash,
  promptVersion,
  schemaVersion
}

Cache entry становится доступным для повторного использования только после прохождения deterministic checks и требуемого semantic quality gate. Нужен статус: candidate → validated → approved → superseded.

Definition of done

Когда можно считать качество управляемым

  • Production не использует deprecated/shutdown preview model.
  • targetLang === nativeLang никогда не требует native-перевода примера.
  • Романизация и target/native duplication автоматически отклоняются.
  • Первый пример для phrase содержит главный перевод или валидную словоформу.
  • sourceUsage сохраняется и одинаково отображается во всех learning views.
  • usageNote и connotationWarning имеют разные продуктовые смыслы.
  • Model/prompt/schema изменения проходят один и тот же evaluation dataset.
  • Есть метрики качества по model и language pair.
  • Cache принимает только validated entries и учитывает context/version.
  • Fine-tuning рассматривается только после накопления исправленных production examples.
Что сознательно отложено. Разбиение каждого перевода на три обязательных LLM-запроса преждевременно. Сначала нужно исчерпать улучшения контракта, модели, validation и targeted repair. Multi-call generation вводится только если benchmark покажет, что single-request не достигает целевых метрик.

Основано на фактической структуре Polyglot: translation prompt/schema/service, validation, context lookup, vocabulary persistence и Telegram renderers.
