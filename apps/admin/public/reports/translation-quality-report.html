Главный вывод

Проблема не в одном неудачном промпте. Система гарантирует корректную форму JSON, но почти не гарантирует содержательную правильность: язык каждого поля, употребление переведённого выражения в примерах, отсутствие транслитерации, корректную связь пояснения с языком.

Два независимых фактора складываются: (1) используемая preview-модель gemini-2.5-flash-lite-preview-09-2025 выключена Google 31.03.2026 — пайплайн работает в неопределённом degraded-режиме ~2,5 месяца; (2) валидаторы пропускают семантически неверные строки, поэтому даже сильная модель будет периодически давать ошибки.

Что крепко в системе

  • Многоуровневый retry: generation error + validation fail → strict prompt (до 2 раз)
  • Dictionary enrichment через Wiktionary (fail-open, не ломает перевод)
  • Per-language output config (можно отключать поля)
  • Чёткая DI: AI-adapter инжектируется, core не зависит от провайдера
  • Structured output через Zod + Vercel AI SDK

Где главный провал

  • validateLanguage() — полный no-op, всегда возвращает valid
  • Проверка headword отключается для любого multi-word выражения
  • frequencyPenalty: 0.5 штрафует повтор главного слова в примерах
  • native требуется даже когда target === nativeLang
  • sourceUsage не сохраняется в БД и не показывается во флешкартах

От ввода слова в Telegram до отображения карточки и сохранения в словарь. Красные узлы — места, где обнаружены дефекты.

2Эксплуатационный кризис модели

Самый срочный и дешёвый фактор качества — и при этом не только вопрос качества.

gemini-2.5-flash-lite-preview-09-2025 выключена Google 31 марта 2026 года. Сегодня 19 июня 2026 — модель отсутствует уже ~2,5 месяца. Пайплайн продолжает работать: OpenRouter молча подставляет fallback-модель в неопределённом degraded-режиме. Это само по себе правдоподобно объясняет существенную часть деградации качества, независимо от дефектов схемы и валидаторов.

Быстрый вариант

gemini-3.5-flash

Актуальная стабильная Flash. Frontier-класс, скорость, цена/performance.

Бюджетный кандидат

gemini-3.1-flash-lite

Рекомендованная Google замена для lite-preview.

Сильный референс

claude-sonnet-4

Для бенчмарка верхнего качества и routing сложных случаев.

Важно: выбор подтверждать мини-бенчмарком (20–30 кейсов из P0), а не предположением. Промпт требует structured output с многоязычными блоками и строгими правилами языка — lite-модели исторически плохо следуют таким инструкциям. Но смена модели не устраняет дефекты контракта: даже сильная модель будет периодически ошибаться, потому что валидаторы пропускают семантически неверные строки. Модель + контракт — два независимых фактора, чинить оба.

3Каталог подтверждённых проблем

14 дефектов, верифицированных по исходному коду. Каждый — с локацией и минимальным фиксом.

Транслитерация латиницей в поле native

P0 · критично
📍 flashcard.renderer.ts:78-83 · translation.schema.ts:32-40 · translation.service.ts:77
Рендерер ставит ex.native в скобки после примера. Для русского блока модель заполняет native романизацией латиницей, для чешского — дублирует чешский текст. Схема требует поле всегда, валидатор языка — no-op.
Фикс: per-language schema (native отсутствует при target===native), deterministic-валидатор «Cyrillic-expected → ноль кириллических кодпоинтов = reject», запрет романизации в основном промпте.

Модель в shutdown-состоянии ~2,5 месяца

P0 · критично
📍 system_settings · ai-model.ts
Preview-модель выключена Google 31.03.2026. OpenRouter молча подставляет fallback. Качество непредсказуемо.
Фикс: мигрировать на gemini-3.5-flash / gemini-3.1-flash-lite, подтвердить мини-бенчмарком.

frequencyPenalty: 0.5 штрафует повтор изучаемого слова

P0 · критично
📍 ai/index.ts:42
Настройка подталкивает модель избегать повторения главного выражения, хотя педагогически его как раз нужно повторить в примерах. Параметр общий для всех callers (chat/detection тоже).
Фикс: параметризовать per-call, translation → 0. Не менять глобально без проверки других callers.

Запрет романизации только в retry-промпте

P0 · высокоimpact
📍 prompt.builder.ts:78-160 vs prompt.builder.ts:188
«No transcription, IPA, romanization» есть только в buildStrictPrompt. Основной промпт этого не говорит — модель не знает, что латинская романизация русского недопустима.
Фикс: добавить правило в основной промпт: «Do not include IPA, romanization, transliteration in any field».

Проверка headword отключается для multi-word выражений

P0 · критично
📍 example.validator.ts:67-76
shouldValidateFirstExampleHeadword возвращает false при наличии пробела. «phase out» содержит пробел → проверка полностью выключена → модель может вернуть любые предложения. Это объясняет «ни одного примера с нужным словом».
Фикс: token-aware / lemma-aware проверка: разбить выражение на токены, проверить что хотя бы один токен (или лемма) присутствует в первом примере.

validateLanguage() — полный no-op

P1 · высокоimpact
📍 language.validator.ts:18
Функция всегда возвращает { valid: true, errors: [] }. Комментарий: franc-min был удалён за ложные срабатывания на коротких текстах. Итог: язык НЕ проверяется нигде — ни у native, ни у connotationWarning, ни у nativeMeaning.
Фикс: комбинированный подход: проверка письменности (Cyrillic/Latin/Han) + детект романизации + native≠target + AI-валидатор для неоднозначных + franc только для длинных строк.

sourceUsage не сохраняется в БД

P1 · высокоimpact
📍 toVocabularyInput() · vocabulary.repository.ts · schema.ts
При сохранении слова sourceUsage теряется. После сохранения восстановить невозможно. Флешкарты/словарь/SRS не могут показать примеры с исходным словом.
Фикс: добавить JSONB-колонку sourceUsage на vocabulary_entries (это metadata исходного выражения), миграция, mapper, repository.create/update.

sourceUsage отображается только в translation renderer

P1 · высокоimpact
📍 flashcard.renderer.ts · dictionary.renderer.ts · srs.renderer.ts
Промпт запрашивает 3 примера на языке источника с переводом на родной, схема требует, сервис делает обязательными — но ни одна карточка кроме карточки перевода их не показывает.
Фикс: протянуть sourceUsage в три рендерера + mapper/repository types.

connotationWarning не показывается во флешкарте

P1 · средне
📍 flashcard.renderer.ts
Helper уже передаёт connotationWarning в WordDisplayData, но рендерер его не отрисовывает. Пользователь не видит предупреждение о коннотации при повторении.
Фикс: добавить отрисовку в flashcard/dictionary/SRS рендереры.

Смешаны sourceUsage / usageNote / connotationWarning

P1 · архитектура
📍 prompt.builder.ts:246 · types.ts
Сейчас connotationWarning опционален и задуман только для редких «опасных» коннотаций. Но пользователь ожидает постоянное пояснение к каждому переводу (оттенок, регистр) на родном языке. Это другая семантика.
Фикс: ввести поле usageNote: всегда, родной язык, описывает translation.text, оттенок/регистр/употребление. connotationWarning оставить для редких рисков. Валидировать связь с target, отсутствие дублирования, отсутствие объяснения исходного слова.

context-lookup берёт только results[0]

P2 · средне
📍 context-lookup.ts:30
Для многозначных слов берётся первый sense из Wiktionary. Нет нормализации (lowercase, Unicode, trim, lemmatization), нет отбора sense по контексту. «bank» в финансовом и географическом контексте получит одно и то же значение.
Фикс: возвращать все senses, нормализовать lookup, выбирать sense по пользовательскому контексту/POS/частоте.

Нет versioned translation cache

P2 · средне
📍 topic_translation_cache (привязан к topicId)
Повторный перевод того же слова = новый платный LLM-запрос. Общего кэша нет. Но кэшировать любые AI-ответы опасно — ошибки станут постоянными.
Фикс: кэш только верифицированных переводов. Ключ: normalized source + source/target langs + native + normalized target set + sense/context hash + output/template config + prompt/schema version. Версионирование промпта — prerequisite.

Нет prompt versioning

P2 · blocker для кэша
📍 prompt.builder.ts
Кэш-ключ ссылается на «prompt/schema version», но в коде нет константы версии. Без неё кэш никогда не инвалидируется и молча подаст устаревшие переводы после правки промпта.
Фикс: ввести PROMPT_VERSION в prompt.builder.ts, bump при каждом изменении. Fold в P1 — кэш без этого невозможен.

Модель не в MODEL_REGISTRY

P2 · низко
📍 models.ts
gemini-2.5-flash-lite-preview отсутствует в реестре → нет данных по стоимости, лимитам, не учитывается в estimateCost. Adapter принимает любой OpenRouter ID, так что на качество не влияет, но ломает observability.
Фикс: при миграции модели добавить новую в реестр с cost-данными.

4Корневые причины

Три независимых системных провала складываются. Каждый фиксится отдельно, но ни один не покрывается другим.

1 · Контракт пропускает семантику

Schema проверяет форму JSON, но не содержимое. validateLanguage — no-op. Headword-чек отключается для phrases. Романизация не детектируется. Сильная модель всё равно будет периодически ошибаться.

  • Переводчик: deterministic validators + per-language schema
  • Архитектурно: разделить usageNote / connotationWarning

2 · Данные теряются по пути

Промпт запрашивает sourceUsage, схема требует, сервис делает обязательным — но toVocabularyInput не сохраняет, а 3 рендерера не показывают. Пользователь видит «нет примеров с нужным словом», хотя данные генерируются.

  • Переводчик: sourceUsage → vocabulary_entries JSONB + 3 рендерера
  • Архитектурно: sourceUsage на entry, не на translation

3 · Модель + параметры

Dead preview-модель + frequencyPenalty: 0.5 + нет запрета романизации в основном промпте. Складывается с фактором 1: lite-модель хуже следует инструкциям, а инструкции и так дырявые.

  • Переводчик: миграция модели + freqPenalty 0 + правило в промпт
  • Архитектурно: model routing по сложности

5Приоритизация: Effort × Impact

Каждая задача — точка. Ось X — усилия (S/M/L/XL), ось Y — ожидаемый impact. Размер — приоритет. Левый-верхний квадрант = делать первыми.

Без метрик смена модели и правки промпта — субъективная оценка. Нужен систематический датасет.

EVAL
11
Создать dataset из реальных проблем. phase out, phrasal verbs, Czech/Russian morphology, target equals native, idioms, false friends, context-dependent words, transliteration leakage. Расширить P0 mini-eval до 200–500 кейсов.
11b

!Риски и корректировки

Подводные камни, выявленные при сверке планов. Учтены в бэклоге выше.

P0 #1 vs P1 #10 — chicken-and-egg. «Подтвердить модель бенчмарком» требует eval-кейсов, но dataset в P1. Решение: собрать мини-eval на 20–30 кейсов inline с P0 (phase out + дюжина phrasal verbs + target==native + transliteration), выбрать модель, затем расширить до 200–500 в P1. Иначе «бенчмарк» субъективен — то, против чего план сам возражает.
frequencyPenalty общий. Хардкод в AI-adapter используется translation, chat, detection. Смена на 0 глобально может сломать chat/detection. Параметризовать per-call (translation→0, остальные — текущее) или проверить остальных callers перед глобальной сменой.
Per-language native schema — 3 слоя, не 1. buildTranslationResultSchema сейчас emits единый shape для всех lang keys. Гетерогенная per-key схема (native required для одних, отсутствует для других) требует: Zod поддерживает, prompt builder должен варьировать per-language инструкции, spike-confirm что Vercel AI SDK structured output не сглаживает per-key-different object schemas. Бюджет — mini spike, не one-liner.
Кэш требует prompt versioning. Кэш-ключ ссылается на «prompt/schema version», но в коде нет константы. Без неё кэш никогда не инвалидируется и молча подаст устаревшие переводы после любой правки промпта. PROMPT_VERSION — prerequisite, fold в P1.
Правило романизации — точный триггер. «Russian native с только Latin = reject» определить как «ожидаемая письменность Cyrillic И строка содержит ноль кириллических кодпоинтов». Иначе русское предложение с цитатой английского бренда попадёт в ложное срабатывание. Mixed-script — исторический источник false positives franc, не повторять ошибку.
Не кэшировать любые AI-ответы. Кэш только верифицированных переводов.
