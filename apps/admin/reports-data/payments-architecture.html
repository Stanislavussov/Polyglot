The constraint that decides everything

Telegram’s Bot Developer ToS: digital goods sold inside a bot must be paid exclusively in Telegram Stars. Third-party providers via BotFather are physical-goods-only and cannot recur. Linking out from the bot to any external checkout for a digital service is a ToS violation — enforcement goes up to removal from the Bot Platform.

In-bot purchases → Stars only. Native subscriptions, fixed 30-day period, ≤ 10,000 Stars/month.
Mollie ≠ alternative, Mollie = second channel. Legal only for purchases originating on our own website, never funneled from the bot.
Core stays provider-agnostic. Both adapters feed the same subscription ledger and entitlements resolver.

Stars ships first. The fiat channel is deferred; when it matters, the choice is Mollie (cheap, VAT is ours) vs Paddle (merchant of record, VAT is theirs).

Subscription lifecycle

Stars inverts the usual problem: Telegram initiates renewals, we never charge. The hard part is that nothing tells us a renewal failed — absence of a payment is the signal.

activerenewal successful_payment every 30 d re-extends · cancelAtPeriodEnd is a flag here, not a state
period end + skew buffer,
no renewal arrived
past_due · graceaccess retained (~48 h) · dunning DM “top up Stars” · late renewal → back to active
grace deadline passes
expireddowngrade to free · win-back DM · reactivation = new subscription row, never resurrection
Purchaseinvoice payload = user + plan + priceVersion + nonce → pre-checkout validates payer & duplicates in ≤ 10 s → grant keyed on unique charge id, extension = max(periodEnd, now) + 30d
Upgrade Plus → Procharge-first: Pro paid → bot-cancels old Plus sub → unused Plus days credited onto Pro at price ratio (our own day-math; Stars has no proration)
Cancelin-bot → editUserStarSubscription, access to period end. Via Telegram settings → no event; caught by the expiry path
Refund/paysupport → admin-approved refundStarPayment → payment flip + entitlement revocation in one transaction; CHARGE_ALREADY_REFUNDED treated as possibly-success (known API bug)

Pitfalls register — 24 researched failure modes, each with its answer

Compiled from Telegram API docs and issue trackers, Mollie docs, and recurring-billing engineering postmortems (Airbnb, Stripe, Lago, Hookdeck et al.). Severity = how badly it bites if unhandled.

Starshigh

No failed-renewal or expiry event; no subscription-list API

Telegram pushes renewals as payments but never tells the bot a subscription lapsed or was cancelled. Naive designs keep entitlements alive forever.

Our answerOwn cron infers expiry from stored subscription_expiration_date; state machine with grace; daily reconciliation via getStarTransactions.

bothhigh

Duplicate event delivery → double grant

Payment updates and webhooks arrive zero-or-more times, never exactly once. Processing twice grants +60 days for one charge.

Our answerpayments.providerChargeId UNIQUE + grant in the same DB transaction (inbox pattern); extension formula max(periodEnd, now)+30d is replay-safe by construction.

Starshigh

Invoice links are forwardable and payable multiple times, by anyone

A paid link stays valid; a forwarded link can be paid by a different user than intended — money lands with no matching entitlement.

Our answerPayload carries intended user id + nonce; pre_checkout_query rejects mismatched payer or an already-active sub.

Starshigh

Telegram allows concurrent duplicate subscriptions per user

Official API text: any number of concurrent subs from the same user. Double Plus, or Plus + Pro simultaneously, is Telegram-legal.

Our answerReject at pre-checkout; DB partial unique index as backstop; if one slips through paid — auto-refund flow.

bothhigh

Provider ↔ local DB status drift

Missed events silently desync entitlements: the classic “downgraded customer keeps premium forever”.

Our answerLocal DB is the entitlement source of truth; daily reconciliation job diffs provider truth vs ledger and repairs; drift metric alerted at > 0.

bothhigh

Refund or chargeback without entitlement revocation

Money returned, access kept. With SEPA (Mollie) the payer can charge back no-questions for 8 weeks — and always wins.

Our answerRefund handler flips payment status and entitlement atomically; SEPA revenue treated as provisional for 8 weeks; revoke on charged_back.

bothhigh

Silently dead renewal cron

A cron that stops firing equals missed webhooks: no expiry processing, no dunning, discovered weeks later.

Our answerSweep is query-driven and idempotent (re-runnable), row-locked per subscription; writes a heartbeat metric with a Grafana dead-man alert.

bothhigh

Race: two concurrent purchases both pass validation

Both requests read “no active sub”, both proceed — double charge, duplicate rows (the classic distributed double-payment case).

Our answerRow-lock per user in the billing service; partial unique index as the last line of defense.

Molliehigh

Mollie classic webhooks: ID-only, unsigned

The webhook body is just id=tr_xxx — no status, no signature. Trusting it, or processing slowly, invites spoofing and retry storms.

Our answerVerify-by-refetch over the authenticated API; unguessable endpoint URL on admin-api; persist → enqueue → 200 fast; idempotent processing.

Starsmedium

10-second pre_checkout_query deadline

Answer late and the purchase fails at the last step — money UX ruined at the worst moment.

Our answerHandler does index-backed reads only — no AI calls, no external HTTP; answer latency monitored.

Starsmedium

User cancels via Telegram settings — bot hears nothing

No update is delivered on user-side cancel; the bot learns only when the renewal never arrives. Client “My subscriptions” UI also lags, confusing users.

Our answerBy design no special handling needed — the inferred-expiry path covers it; support docs note the client UI lag.

Starsmedium

refundStarPayment lies on recurring charges

Known bug: refunding a subscription charge can return 400 CHARGE_ALREADY_REFUNDED while the refund actually succeeded (tdlib #690).

Our answerTreat that error as possibly-success; verify via getStarTransactions; never blind-retry a refund.

Starsmedium

No test Stars, renewals can’t be time-compressed

The test server has no Star faucet; a real renewal takes 30 days. Untested renewal paths are where billing bugs live.

Our answerClock-injected billing core; integration tests replay successful_payment fixtures duplicated and out of order; one real-money smoke test with self-refund.

Starsmedium

Stars economics: ~32% leakage and a 21-day hold

Users buying Stars on iOS/Android embed the 30% store cut; withdrawal nets ≈ $0.013/Star after a 21-day hold — pricing off the sticker price overstates revenue by a third.

Our answerPrice plans off the $0.013/Star withdrawal rate; cash-flow lag documented in the finance notes.

bothmedium

Out-of-order events

Providers guarantee delivery, not order — a cancellation can arrive before the creation it cancels.

Our answerHandlers converge to the same state in any arrival order; on webhooks, always re-fetch current object state — the event is a doorbell, not the truth.

bothmedium

Upgrade paid but plan not flipped — or flipped but not paid

Half-applied upgrades either give Pro for free or take money without upgrading.

Our answerCharge-first ordering: entitlement changes happen only inside the payment-success transaction.

bothmedium

Price change reprices existing subscribers

Editing the plan row silently changes what active subscribers pay — churn spike and support fires.

Our answerImmutable plan_prices versions; each subscription pins its version at purchase; new prices affect new purchases only.

bothmedium

Cancellation semantics confusion

Immediate cancel with no refund breeds chargebacks; users expect access until what they paid for runs out.

Our answerDefault cancelAtPeriodEnd (undoable, access retained); immediate revocation reserved for refund/fraud; post-expiry return = fresh subscription.

bothmedium

Calendar math: Jan 31 + 1 month, DST, epoch drift

Naive +30 days drifts billing days forever; month-end anchors and DST produce double or missed charges.

Our answerStars fixes the period at 30 days (Telegram computes it); our math is only max()+30d and day-credits; any future fiat cycle uses calendar-aware arithmetic, explicit anchor, UTC storage.

bothmedium

Involuntary churn — renewals fail from empty balance, not intent

20–40% of subscription churn is failed payments the user never noticed (empty Star balance here; expired cards on fiat).

Our answerBot DMs are the dunning channel: T-3 “expires soon” reminder, past_due notice with top-up deep link, win-back after expiry. Telegram’s own low-balance nag helps.

Molliemedium

Card mandates die silently

One chargeback or an expired card invalidates a Mollie card mandate; no account-updater exists — renewals just stop.

Our answerMonitor mandate status, prompt re-checkout DM/email; prefer SEPA DD for EU (€0.35 flat, mandates never expire); charge on our own schedule so state stays in our DB.

Molliemedium

Mollie auto-cancels subscriptions after failed retries — without an event

The Subscriptions engine retries SEPA up to 5×, then cancels; there is no subscription.canceled webhook — you find out from silence.

Our answerSkip Mollie’s engine entirely: charge via Payments API on our own cron; our state machine owns retries, grace, and cancellation.

Molliemedium

EU VAT on digital services

B2C digital services are taxed at the customer’s country; as merchant of record with Mollie, OSS registration and quarterly filings are ours. Ignoring VAT is an existential finance bug.

Our answerDecision gate before Phase 3: Mollie + OSS self-filing vs Paddle as merchant of record (~3pp dearer, zero tax burden). Stars phase carries no such burden.

bothmedium

Trial abuse (if trials are ever added)

Multi-accounting for repeated trials burns real AI-token costs and poisons conversion metrics.

Our answerOne trial per Telegram user id, recorded permanently; trials are out of scope until Stars billing is stable.

Roadmap

Phase 0 is deliberately provider-free: every safety mechanism is built and tested against the mock before real money flows.

Phase 0 · Billing core hardening
  • New tables + migrations: payments, payment_events, plan_prices; extend subscriptions
  • State machine + idempotent billing service in packages/core
  • Injected clock; PaymentPort v2
  • Spec-first tests: replayed, duplicated, out-of-order fixtures
Phase 1 · ⭐ Stars go-live
  • Stars adapter: invoice, pre-checkout, successful-payment handlers
  • Renewal sweep v2: inferred expiry + grace
  • Cancel & upgrade flows
  • /paysupport + refund path
  • Real-money smoke test, self-refunded
Phase 2 · Resilience & ops
  • Daily reconciliation + drift alerts
  • Dunning / reminder DMs
  • Grafana dashboard: renewal rate, drift, heartbeat
  • Admin: ledger view, refunds, manual comp, price versions
Phase 3 · € Web fiat channel (optional)
  • Mollie vs Paddle decision (VAT appetite)
  • Landing-page checkout; never reachable from the bot
  • Webhook ingress on admin-api
  • Mandate lifecycle + SEPA dunning
