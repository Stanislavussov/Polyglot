Telegram-бот для изучения нескольких языков одновременно. Один ввод — переводы на все целевые языки сразу, с CEFR-уровнем, регистром, синонимами и примерами.

1. Что это за приложение и зачем

Polyglot решает конкретную проблему: человек, изучающий 2+ иностранных языка одновременно, знает слово в одном языке, но забывает в другом. Существующие приложения работают только с одной языковой парой — нужно искать одно и то же слово в разных инструментах.

Polyglot — это Telegram-бот. Пользователь вводит любое слово, фразу или предложение, и получает переводы на все свои целевые языки одновременно в одном сообщении. Каждый перевод enriched: CEFR-уровень, регистр (slang/formal/neutral), синонимы, транскрипция, примеры употребления, коннотационные предупреждения.

2. Слои архитектуры и правила зависимостей

Polyglot — это TypeScript monorepo (pnpm workspaces) с тремя чёткими слоями. Правила зависимостей машино-проверяемы через dependency-cruiser (конфиг в .dependency-cruiser.cjs).

📦 packages/core — доменная логика (чистая)

Не знает про Telegram, про БД, про OpenRouter. Только бизнес-логика: перевод, валидация, i18n, SRS, topics, language-detect. Не импортирует ни один @polyglot/* пакет.

↓ импортируется слоями ниже
📦 packages/adapters — платформенно-зависимые адаптеры

db (Drizzle + PostgreSQL), ai (OpenRouter через Vercel AI SDK), notifications (node-cron). Адаптеры не импортируют друг друга и не импортируют infra.

↓
📦 apps — приложения (точки входа)

bot (grammY), admin-api (Fastify), admin (Astro + Vue). Только здесь живут composition root и framework-specific код.

📦 packages/infra — конфиг и логирование

config.ts (Zod-валидация env), логгер. Не импортирует адаптеры AI/notifications.

Скрытая логика: порты (ports) вместо прямых импортов

Core не импортирует адаптеры напрямую. Вместо этого в packages/core/src/ports/ определены интерфейсы: AIPort, UserRepository, VocabularyRepository, LanguageCachePort, SettingsPort, и т.д. Они агрегированы в ServiceContainer. Реализации (из адаптеров)注入ятся в composition root (apps/bot/src/container.ts). Core вызывает AI через функцию, которую ему передали, а не через import.

5. AI-конвейер: промпт → генерация → валидация → ретрай

Это самое сложное место в приложении. Конвейер обеспечивает качество перевода через многоуровневую валидацию и retry с feedback.

5.1 Промпт-билдер (prompt.builder.ts)

Промпт конструируется динамически на основе: source/target языков, nativeLang, inputType (word/phrase/sentence), topic (context hint), dictionaryContext (Wiktionary), outputConfig (включённые/выключенные поля).

// Структура промпта (из buildTranslationPrompt):
"Translate \"word\" from Russian to Czech, English."

// + topic hint (если есть):
"IMPORTANT - User Context Hint: The word should be understood in this context: \"medicine\"."

// + dictionary hint (если есть Wiktionary context):
"IMPORTANT — Authoritative Dictionary Context (Wiktionary):
 Word: \"lékař\" (Czech), part of speech: noun.
 The verified meaning of this word is: \"doctor\", \"physician\"."

// + rules (динамические, зависят от config):
"Return ONLY valid JSON matching the provided schema."
"For each target language: translation text; 2-3 close synonyms;
 exactly 2 alternative translations; exactly 3 short examples with
 native translations; usageNote; connotationWarning only when relevant."
"VARIETY IN EXAMPLES IS MANDATORY: Each of the 3 examples MUST use
 a DIFFERENT word or expression."
"Idiomatic & Proverb Rule: if no direct equivalent, provide CLOSEST
 FUNCTIONAL EQUIVALENT, set expressionType to \"idiomatic_equivalent\"."

5.2 Zod-схема ответа (translation.schema.ts)

Схема динамическая — buildTranslationResultSchema() строит её под конкретный запрос с обязательными ключами для каждого target-языка. Это заставляет AI SDK возвращать все ожидаемые переводы.

// Структура TranslationResult (из types.ts):
{
  emoji: string,                              // один эмодзи
  nativeMeaning?: string,                     // значение на родном языке
  sourceUsage?: {                             // если source = изучаемый язык
    explanation: string,                      //   когда использовать
    synonyms: Synonym[],                      //   синонимы в source-языке
    examples: Example[]                       //   примеры в source-языке
  },
  nativeSynonyms: Synonym[],                  // синонимы исходного слова на родном
  translations: {
    "cs": {
      text: string,                           // основной перевод
      synonyms: Synonym[],                    // 2-3 синонима
      examples: Example[],                    // ровно 3 примера
      expressionType?: "literal"|"idiomatic_equivalent",
      equivalentNote?: string,                // пояснение к идиоме
      usageNote?: string,                     // нюансы употребления
      alternatives?: TranslationVariant[],    // ровно 2 альтернативы
      connotationWarning?: string             // предупреждение о коннотации
    },
    "en": { ... }
  }
}

// Example = { context, target, native? }
// Synonym = { text }
// TranslationVariant = { text, synonyms[] }

5.3 Retry с strict prompt

Если AI-ответ не проходит валидацию, промпт перестраивается с явным указанием ошибок:

// buildStrictPrompt() добавляет:
"IMPORTANT: Your previous response had validation errors:
  - [examples-variety] examples: all 3 examples use the same word
  - [native-meaning] nativeMeaning: missing required field

Please fix these issues and return a corrected JSON response.
Double-check that:
  - Each of the 3 examples uses a DIFFERENT word
  - Top-level nativeMeaning is present and written in Russian
  - Every target block has a usageNote
  - No transcription, pronunciation, IPA, romanization"

5.5 Валидация (validation/ модуль)

Функция validate() проверяет AI-ответ на нескольких уровнях:

  • Schema validation — структура соответствует Zod-схеме
  • Language validation — перевод действительно на нужном языке (не копия исходного)
  • Semantic validation — перевод имеет смысл, не пустой
  • Examples validation — примеры используют разные слова (variety rule)

Каждое нарушение получает { rule, field, message }. Все ошибки собираются и передаются в buildStrictPrompt() для следующей попытки.

5.6 NeedsReview flag

Если все 3 попытки провалились — результат всё равно возвращается пользователю, но с needsReview: true. Это graceful degradation — лучше показать несовершенный перевод, чем ничего.

5.7 Context enrichment — скрытый слой качества

Перед каждым AI-запросом translateWithContext() ищет слово в таблице word_context (данные из Wiktionary/kaikki.org). Если найдено однозначное совпадение — POS, glosses, form tags добавляются в промпт как "Authoritative Dictionary Context". Это помогает AI выбрать правильный смысл слова. Fail-open: при ошибке lookup перевод продолжается без контекста.

5.8 Post-processing: stripDisabledFields + sanitizeEmoji

AI может вернуть поля, которые пользователь отключил в template. stripDisabledFields() зануляет их после генерации. sanitizeEmoji() проверяет, что в поле emoji действительно эмодзи (не синоним-слово) — fallback "🔤".

Скрытая логика: vocabulary_translations — это и перевод, и SRS-карта

Вместо отдельной SRS-таблицы, колонки srsEaseFactor, srsInterval, srsDueDate, srsReviewCount живут прямо в vocabulary_translations. Один ряд = одна карточка для одного языка. Каждая пара (entry, targetLang) имеет свой SRS-график. Это значит: если пользователь учит 3 языка, одно сохранённое слово = 3 независимые SRS-карты.

7. Dependency Injection и composition root

Polyglot использует вручную сконструированный DI-контейнер — не tsyringe/awilix, а простой объект с интерфейсами.

Порты (interfaces) — в packages/core/src/ports/

12 port-интерфейсов определяют контракты, которые core ожидает от адаптеров:

  • AIPort — generateObject(), generateText(), generateChat(), getAvailableModels(), estimateCost()
  • UserRepository — findByTelegramId(), getSettings(), updateActiveMode(), updateLastInteraction()
  • VocabularyRepository — create(), findByOriginalAndSource(), updateTranslation()
  • VocabularyDictionaryRepository — addEntryToDefault(), entryBelongsToDefault()
  • LanguageCachePort — getLang(), getAllLangs(), getSupportedLangs(), normalizeToIso1()
  • SettingsPort — getPlanLimit(), AI defaults, SRS config, notification defaults
  • и др.: NotificationRepository, TranslationRequestRepository, TranslationTemplateRepository, WordReviewRepository

ServiceContainer — агрегация всех портов

// packages/core/src/ports/container.ts
export interface ServiceContainer {
  userRepository: UserRepository;
  vocabularyRepository: VocabularyRepository;
  vocabularyDictionaryRepository: VocabularyDictionaryRepository;
  translationTemplateRepository: TranslationTemplateRepository;
  wordReviewRepository: WordReviewRepository;
  notificationRepository: NotificationRepository;
  translationRequestRepository: TranslationRequestRepository;
  languageCache: LanguageCachePort;
  ai: AIPort;
  settings: SettingsPort;
}

Composition Root — apps/bot/src/container.ts

Единственное место, где adapter-реализации связываются с port-интерфейсами:

// apps/bot/src/container.ts
export function createContainer(): ServiceContainer {
  // Wire AI metric sink → DB
  setAIRequestMetricSink((log) =>
    aiRequestLatencyRepository.record({ ...log })
  );

  const settings = new SettingsService(settingsAdapter);

  return {
    userRepository,              // from @polyglot/adapter-db
    vocabularyRepository,
    vocabularyDictionaryRepository,
    translationTemplateRepository,
    wordReviewRepository,
    notificationRepository,
    translationRequestRepository,
    languageCache: { loadLanguageCache, getLang, getAllLangs, ... },
    ai: { generateObject, generateText, generateChat, getAvailableModels, estimateCost },
    settings,
  };
}

Как контейнер попадает в handlers

index.ts → createPolyglotBot({ services: createContainer() }) ↓ bot-factory.ts: bot.use((ctx, next) => { ctx.services = services; ← ← ← внедрение в каждый ctx return next(); }); ↓ translate-mode.helper.ts: ctx.services.ai.generateObject(...) ← вызов AI через порт ctx.services.vocabularyRepository.create(...) ← запись в БД через порт ctx.services.settings.getPlanLimit(...) ← настройки через порт
Почему так: Core (бизнес-логика) не импортирует адаптеры. Он описывает порты, а composition root в apps/bot связывает реализации. Это позволяет: (1) мокать адаптеры в тестах core, (2) заменить OpenRouter на другого провайдера, изменив только адаптер + composition root, (3) dependency-cruiser гарантирует, что core остаётся чистым.

8. Уведомления и планировщик

Уведомления живут в packages/adapters/notifications/. Это полностью автономный модуль: не импортирует bot, не импортирует AI, не импортирует DB-репозитории напрямую. Всё внедряется через deps.

Архитектура планировщика (scheduler.ts)

  • Один cron-job на всех пользователей — не job-per-user. Расписание: */30 * * * * (каждые 30 минут)
  • На каждом тике: вычисляет UTC hour + minute, находит пользователей, чьё локальное время совпадает с их notificationTime
  • Для каждого пользователя: pick word → send → record в notification_history
  • В полночь UTC: отдельный проход processInactiveUsers() — 14 дней неактивности → re-engagement сообщение + disable notifications

Выбор слова (notification.service.ts)

notificationTypeЛогика pickSource
srs (default)Случайное слово из словаря пользователя, исключая recently sentpickDictionaryWord()
contextualAI генерирует предложение по контексту пользователя (например "preparing for job interview")pickContextualWord() — generateObject с sentence schema
suggestedAI-предложение нового словачерез deps

Retry и resilience

  • retryWithBackoff() для DB-операций: 3 попытки, exponential backoff (1s, 2s, 4s)
  • sendWithRetry() для Telegram: 3 попытки с задержками [1s, 2s, 4s]
  • Rule: log and continue — никогда не останавливать scheduler. Ошибка одного пользователя не блокирует остальных
  • Catch-all safety net: весь tick обёрнут в try/catch — cron не должен крашиться

Wiring — apps/bot/src/notifications/notification.wiring.ts

Composition root для notifications: связывает scheduler с реальными deps (репозитории из DB-адаптера, AI-генерация, i18n функция t) и bot.api.sendMessage как sendFn. Вызывается из index.ts после старта бота.

9. Spaced Repetition (SM-2)

Алгоритм SM-2 реализован в packages/core/src/modules/srs/sm2.ts — 54 строки чистой функции, без состояния.

Типы

// types.ts
type SrsRating = "again" | "hard" | "good" | "easy";

interface SrsState {
  easeFactor: number;   // начинается с 2.5
  interval: number;     // в днях; 0 = ещё не повторялось
  reviewCount: number;
  dueDate: Date | null;  // null = unscheduled, считается "due"
}

interface SrsReviewResult extends SrsState {
  rating: SrsRating;
  dueDate: Date;         // всегда задан после review
}

Логика пересчёта интервала

RatingИнтервалEase Factor Δ
again1 день (сброс)−0.20
hardmax(1, interval × 1.2)−0.15
good1 → 6 → interval × easeFactor±0 (без изменений)
easy4 (первый раз) / interval × easeFactor × 1.3+0.15

Ease Factor ограничен снизу: Math.max(1.3, value). Первая серия: good → 1 день, потом 6 дней, потом interval × easeFactor.

Где хранится SRS-состояние

В vocabulary_translations — колонки srs_ease_factor (default 2.5), srs_interval (default 0), srs_due_date (nullable), srs_review_count (default 0). Индекс vt_srs_due_idx на srsDueDate для быстрого поиска due-карточек.

Review flow

/review command → srs.scene.ts::handleReviewCommand ↓ Запрос due-карточек: vocabularyRepository.getSrsDueCards(userId, limit=20) ↓ Для каждой карточки: ├─ Показ: emoji + original + "reveal" button ├─ srs:reveal → показать переводы ├─ srs:rate:again|hard|good|easy → applySm2Review(state, rating) │ └→ vocabularyRepository.updateSrsState(entryId, langId, result) └→ следующая карточка или "done"

12. Ключевые архитектурные решения

1. Core не знает про Telegram. Все 12 модулей в packages/core — чистая бизнес-логика. Bot-layer (grammY) вызывает core-функции, передавая AI-генератор и репозитории через DI. Это проверяется dependency-cruiser.
2. Один AI-запрос = все языки сразу. Промпт просит перевести на все target-языки в одном вызове generateObject(). Zod-схема динамически строится с обязательными ключами для каждого языка. Это core USP продукта — "multi-language in one request".
3. Validation-retry loop с feedback. AI-ответ валидируется на 4 уровнях. При failure — retry с strict prompt, содержащим конкретные ошибки. До 3 попыток. При полном провале — needsReview: true (graceful degradation, а не пустой ответ).
4. Context enrichment (Wiktionary) — fail-open. Перед AI-запросом ищется offline-словарный контекст. Если найден — enriches промпт как "Authoritative Dictionary Context". При ошибке — перевод продолжается без контекста. Качество улучшается, но не блокируется.
5. Session в PostgreSQL, не в памяти. createPostgresSessionStorage() хранит grammY sessions в таблице bot_sessions. Перезапуск бота не теряет состояние: activeMode, pendingTranslation, translationMap, flashcard/srs/dictionary wizard state — всё переживает рестарт.
6. SRS живёт прямо в vocabulary_translations. Нет отдельной SRS-таблицы. Колонки srs_ease_factor, srs_interval, srs_due_date, srs_review_count — на каждом переводе. Одна запись слова = N независимых SRS-карт (по одной на target-язык).
7. Rate limiting через credit system. Тарифы (rate_limit_plans) определяют creditsPerDay и creditCost. Каждый перевод списывает кредиты. translation_requests логирует каждый запрос. Admin может менять планы и assigns пользователей. AI-доступ к моделям тоже gated по плану (ai_model_plan_access).
8. Notifications — полностью автономны. Scheduler не импортирует bot. sendFn внедряется. На ошибке — log and continue, никогда не крашится. Retry с backoff для DB и Telegram. 14-day inactivity → auto-pause + re-engagement.
9. Language detection: sync → async → mistype flow. Сначала быстрый sync-детектор (скрипт + диакритики + franc). Если не уверен — async AI-детектор через generateText. Если и AI не определил — mistype flow: показывает warning + Confirm/Cancel кнопки, записывает событие в language_detection_events для аналитики.
10. Метрики на каждом уровне. ai_request_latencies — каждый AI-запрос (model, tokens, cost, duration). translation_request_timings — сегментные метрики (preflight / dbLookup / aiRequest / total). language_detection_events — mistype-аналитика. Prometheus-совместимый metrics server на :9090 (apps/bot/src/metrics.ts).
11. User templates управляют AI-запросом. Не просто UI-фильтр — resolveOutputConfig() передаётся в buildTranslationResultSchema(), и Zod-схема реально меняется. Если пользователь отключил examples — AI их не запрашивает (экономия токенов). Но stripDisabledFields() дополнительно зануляет на случай, если модель всё равно их вернёт.
12. Partial regeneration с auto-update. Кнопка tr:regen:{lang} перезапрашивает только один язык через translateOneWithContext() — дешевле полного перевода. Если слово уже сохранено (savedWordId), результат автоматически обновляет запись через vocabularyRepository.updateTranslation(). Пользователь не видит "re-save prompt" — frictionless refinement.
