## Проблема

`packages/adapters/db/drizzle/` содержит дубли номеров: `0015_closed_pepper_potts.sql` и `0015_custom_notification_time.sql`, `0017_notification_history.sql` и `0017_cuddly_slipstream.sql`; номера 0018 нет. **`0015_custom_notification_time.sql` отсутствует в `meta/_journal.json`** — мёртвый файл, который никогда не применится, но апдейтит `notification_time` (колонку, позже переименованную). Порядок применения держится только на журнале. Плюс `0002` всё ещё вставляет `iso3_code` (валидно только потому, что на свежей БД идёт до `0007_drop_iso3_code`) — мина при squash/пересборке истории.

## Затронутые файлы

- `packages/adapters/db/drizzle/0015_custom_notification_time.sql` (мёртвый).
- `packages/adapters/db/drizzle/meta/_journal.json`.
- `packages/adapters/db/drizzle/0002_*.sql` (риск `iso3_code`).

## Решение

1. Удалить осиротевший `0015_custom_notification_time.sql` (не в журнале, колонка переименована).
2. Задокументировать в `@docs/`, что **нумерация файлов ≠ порядок применения**; источник порядка — `_journal.json`.
3. Зафиксировать риск `0002`/`iso3_code`: не делать squash истории без переписывания seed-миграций от текущей схемы (CLAUDE.md уже предупреждает про 42703 — усилить).
4. Свериться с политикой из CLAUDE.md Hard Rule #3 (seed-колонки брать из текущего `schema.ts`, не копировать из старых INSERT).

## Критерии приёмки

- [ ] Мёртвый файл удалён; `pnpm db:check` без дрейфа.
- [ ] Документирован принцип «журнал = источник порядка».
- [ ] Свежая миграция с нуля (`db:migrate` в CI-подобной среде) проходит без 42703.

## Тесты (spec-first)

- `pnpm db:check` — нет расхождений схемы с журналом.

`db:migrate` на develop запрещён (CLAUDE.md) — проверку «с нуля» делать в CI-подобной среде, локально только `db:generate`/`db:push`. Координация с expand/contract [T13](T13-deploy-health-gate-rollback.md).
