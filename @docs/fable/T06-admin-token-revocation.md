# T06 — Ревокация JWT / проверка `isActive` в рантайме

- **Приоритет:** P1 (High)
- **Фаза:** 1 — Безопасность
- **Оценка:** ~1.5 дня
- **Зависит от:** —
- **Блокирует:** [T07](T07-admin-rbac-auth-hook.md) (общий auth-хук)
- **Связано:** [T05](T05-admin-login-rate-limit.md), [T27](T27-admin-service-layer-contracts.md)
- **Находки:** S4

## Проблема

`apps/admin-api/src/routes/auth.ts:16,32-39` — `isActive` проверяется **только** при логине. Все прочие маршруты и `/me` делают лишь `jwtVerify`, поэтому заблокированный или удалённый админ сохраняет полный доступ до истечения токена (24 ч, `auth.ts:25`). Нет ни blacklist, ни `tokenVersion`, ни ротации `JWT_SECRET`.

## Затронутые файлы

- `apps/admin-api/src/routes/auth.ts:16,25,32-39`.
- `apps/admin-api/src/plugins/auth.ts` — место для рантайм-проверки.
- Схема админов (для `tokenVersion`, если выбран этот путь).

## Решение

Выбрать по трейд-оффу:

1. **Рантайм-проверка `isActive`** в auth-хуке: подгружать админа при каждом запросе и проверять `isActive`, с коротким in-memory кэшем (например 30–60 с), чтобы не бить БД на каждый запрос. Просто, закрывает деактивацию.
2. **`tokenVersion`**: колонка у админа + в claims; несовпадение → отказ. Инвалидирует все токены админа при смене пароля/деактивации.
3. Долгосрочно — короткий access-token + refresh (перекликается с [T11 в admin](T27-admin-service-layer-contracts.md) и хранением токена, S11/[T30](T30-longtail-cleanup.md)).

Минимум для этой задачи — вариант 1 (или 1+2).

## Критерии приёмки

- [ ] Деактивированный админ теряет доступ ко всем маршрутам в пределах TTL кэша (не через 24 ч).
- [ ] Проверка не добавляет запрос к БД на каждый вызов (кэш работает).

## Тесты (spec-first)

- Integration-тест: логин → деактивация в БД → по истечении TTL кэша защищённый маршрут отдаёт 401.
- Тест, что активный админ не получает лишних отказов.

## Примечания

Реализовать рантайм-проверку в едином хуке — это подготовка к [T07](T07-admin-rbac-auth-hook.md), где 11 копий хука сводятся в один.
