# T19 — LRU-эвикция `translationMap` в сессии

- **Приоритет:** P1 (High — деградация со временем)
- **Фаза:** 2 — Устойчивость и наблюдаемость
- **Оценка:** ~1 день
- **Зависит от:** —
- **Блокирует:** [T22](T22-refactor-translate-helper-di.md) (тот же файл/сессия)
- **Связано:** [T01](T01-mentor-session-validator.md)
- **Находки:** B6

## Проблема

`apps/bot/src/types.ts:45-59` + запись в `translate-mode.helper.ts:844-850` — на каждую карточку в `translationMap` кладётся полный `TranslateOutput` + grammar + etymology; **ни одного `delete` по ключу в коде нет**. Строка сессии активного пользователя (в Postgres) пухнет месяцами; каждый апдейт читает/пишет её целиком (сериализовано `sequentialize`) → деградация латентности всех апдейтов активного пользователя.

## Затронутые файлы

- `apps/bot/src/types.ts:45-59` — структура `translationMap`.
- `apps/bot/src/scenes/helpers/translate-mode.helper.ts:844-850` — запись.
- `apps/bot/src/session-storage.ts` — сериализация сессии.

## Решение

1. LRU-эвикция: хранить только последние N карточек (например 20–50); при добавлении вытеснять старые.
2. При промахе по ключу (карточка вытеснена) — показывать уже существующий алерт «Session expired» (та же ветка, что в out-of-set diff, [T02](T02-finish-out-of-set-diff.md)).
3. Рассмотреть хранение тяжёлых полей (grammar/etymology) вне сессии (в БД по entry) — но минимум это LRU.

## Критерии приёмки

- [ ] Размер `translationMap` ограничен сверху N ключами.
- [ ] Обращение к вытесненной карточке даёт корректный «expired»-ответ, не ошибку.
- [ ] Латентность апдейтов активного пользователя не растёт со временем.

## Тесты (spec-first)

- Тест: после N+M карточек в map ≤ N ключей, вытеснены самые старые.
- Тест: callback по вытесненному ключу → «session expired», без исключения.

## Примечания

Делать до/вместе с распилом helper'а [T22](T22-refactor-translate-helper-di.md), чтобы эвикция уехала в извлечённый pipeline корректно.
