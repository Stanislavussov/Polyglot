# T15 — Безопасный `bot.catch` с ответом пользователю

- **Приоритет:** P1 (High)
- **Фаза:** 2 — Устойчивость и наблюдаемость
- **Оценка:** ~0.5 дня
- **Зависит от:** —
- **Блокирует:** —
- **Связано:** [T14](T14-telegram-429-403-resilience.md)
- **Находки:** B3

## Проблема

`apps/bot/src/bot-factory.ts:320-336` — `bot.catch` только логирует: пользователь при неперехваченной ошибке не получает ничего (замерший «Translating…» — ровно сценарий инцидента с 429). Хуже: строка 332 читает `ctx.session.activeMode` — если ошибка случилась **до** session-middleware (в `updateMetricsMiddleware` или `sequentialize`), обращение к `ctx.session` бросит исключение **внутри обработчика ошибок** → unhandled rejection в runner. Нет различения `GrammyError`/`HttpError`.

## Затронутые файлы

- `apps/bot/src/bot-factory.ts:320-336`.

## Решение

1. Обернуть тело `bot.catch` в try/catch — сам обработчик не должен падать.
2. Безопасный доступ к `ctx.session` (может отсутствовать) — не читать его без проверки.
3. Best-effort реплай пользователю («что-то пошло не так, попробуйте ещё раз») — чтобы не оставлять зависший индикатор.
4. Классификация ошибок: `GrammyError` (ошибка Telegram API) vs `HttpError` (сеть) vs прикладная — разное логирование/реакция (согласовать с [T14](T14-telegram-429-403-resilience.md)).

## Критерии приёмки

- [ ] Ошибка до session-middleware не вызывает unhandled rejection.
- [ ] Пользователь получает понятное сообщение об ошибке (когда возможно ответить).
- [ ] Типы ошибок различаются в логах.

## Тесты (spec-first)

- Тест: ошибка в middleware до сессии → `bot.catch` не бросает, best-effort реплай не падает.
- Тест: прикладная ошибка в хендлере → пользователь получает сообщение, «Translating…» не зависает.

## Примечания

Малый объём, большой эффект на UX при сбоях. Делать вместе с [T14](T14-telegram-429-403-resilience.md) (общая классификация ошибок).
