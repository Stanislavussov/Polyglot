# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- **Technical bot messages are now swept consistently, and content messages are guaranteed never to be.** The chat accumulated scaffolding forever: mode confirmations ("Translate mode on"), validation rejections (emoji-only, digits-only, too long, `#context` with no word), quota and error notices, dictionary wizard replies, empty-state messages, and the report-issue prompts all stayed on screen indefinitely. The machinery to clear them existed (`trackTechnicalMessage` / `cleanupTechnicalMessages`) but covered barely half the call sites — and `replyTechnical`, the wrapper meant to make the rule automatic, had **zero** callers. Worse, the sweep itself ran in only a handful of places, so "stays forever" was the default and deletion the exception. Every technical message left hanging with an inline keyboard is also a future dead button: Telegram refuses to edit a message past 48 hours, which is exactly the failure mode behind the "message to edit not found" class of bugs. Now: **one** way to send a technical message (`replyTechnical`, used at all ~50 such sites), and **one** central sweep — `technicalCleanupMiddleware` clears the previous interaction's scaffolding on every new user message, before any handler runs. Callback queries are deliberately excluded (a tap usually acts *on* a tracked menu, and sweeping there would delete the keyboard under the user's finger); the handlers that end such a flow still sweep explicitly, and an update consumed by a running conversation keeps its prompts until the dialog finishes. Content — translation cards and regenerated cards, detailed 🔬 analyses, mentor answers, notifications and activation nudges, video vocabulary results, onboarding hook cards and the completion screen — is sent with a plain `ctx.reply` and is structurally unsweepable, since only `replyTechnical` writes to the ledger. Two ordering bugs fell out of making the rule uniform and are fixed: `handleTranslateText` swept mid-flow, which deleted the one-time main-menu hint that `mainKeyboardMiddleware` had attached to the very message being translated (it now only sweeps on the callback-driven entries — retry, activation nudge — that bypass the central middleware), and the notification-context handler swept *after* sending its confirmation, deleting it instantly. The ledger is also capped at 50 ids, oldest dropped first, so a chat whose messages have all aged past the 48-hour deletion window cannot grow the Postgres-backed session without bound. Deliberate exceptions, both documented at their call site: the timeout notice with the "🔄 Try again" button (the retry handler deletes it itself, and a sweep must not remove the button mid-thought), and the background video-processing result, which is sent from a task with no live session to write to.

- **AI model routing is now explicit and fully database-driven — no model id is hardcoded anywhere.** The failover ("fallback") model used to be a constant in the bot (`FALLBACK_AI_MODEL`), and the AI Models page offered per-model *plan checkboxes* whose effect on routing was implicit: a plan got the global default model if the plan happened to be allowed to use it, otherwise the alphabetically first allowed model — invisible in the UI and impossible to predict. The plan/model junction (`ai_model_plan_access`) drove nothing else; its only reader was that rule.

  The AI Models page now opens with a **Model routing** panel: one dropdown per subscription plan ("Use default model" or a specific model), one for the **default model** (plans without their own choice, background jobs), and one for the **fallback model** ("No fallback" is a valid choice — the call then runs a single unsplit attempt). The table below is a plain catalog with a "Used for" column listing each model's roles (Default / Fallback / plan labels), plus enable/disable and delete. Resolution order, shown literally by that panel: the plan's model → the default model → the fallback model → `AIModelNotConfiguredError`. Every step is a row an admin can change without a redeploy.

  Guards match the routing model: a disabled model can be neither the default, nor the fallback, nor a plan's model; a model holding any role can be neither deleted nor disabled, and the error names the roles blocking it. Migration `0046` adds `ai_models.is_fallback` and `rate_limit_plans.ai_model_id` (FK, `ON DELETE SET NULL`) and **drops `ai_model_plan_access`** — plans start with no model of their own and follow the default until routed explicitly, which matches how the previous rule behaved for a default model allowed on every plan.

  Behavioral consequence worth knowing: with no hardcoded model left, a database that names no model at all (empty `ai_models`, or all models disabled) now surfaces `AIModelNotConfiguredError` instead of quietly calling a compiled-in slug. That is the failure mode this change is for — the 2026-07-17 outage was a hardcoded fallback holding `google/gemini-3.1-flash`, an id OpenRouter rejects, so every primary timeout hard-failed on a model no admin could fix.

### Added

- **Icons on every bot command, and the everyday entry points moved out of the command list into a persistent menu under the input field.** The Telegram command menu was an unlabelled wall of eight same-looking rows, so nothing was distinguishable at a glance. Two changes: (1) every command description is now prefixed with an emoji (`🚀 /start`, `🔤 /translate`, `📝 /template`, `⚙️ /settings`, `🐛 /report`, `🆕 /changes`), taken from a single `COMMAND_ICONS` map in `commands/commands.ts` rather than baked into the locale files — the icons are language independent, so all 11 locales get them without touching a translation (and the existing `t("cmdDesc…")` assertions keep passing unchanged). (2) `/dictionary`, `/flashcard` and `/videos` — the three things a user taps every session, as opposed to configuring once — are no longer advertised in the command list. They are now a **persistent reply keyboard** under the input field — one single row, `📖 Dictionary` · `🎴 Cards` · `🎬 Videos` (`utils/main-menu.ts`, `resized().persistent()` so it stays open instead of collapsing behind the keyboard icon) — leaving the command menu to the rare configuration-style actions. One row rather than 2 + 1 because the keyboard is persistent, so every extra row permanently costs chat space. That imposes a width budget — a 360dp-wide chat leaves ~104dp per button — which two translations broke: `menuBtnDictionary` in French (`Dictionnaire`) and `menuBtnFlashcards` in Kazakh (`Карточкалар`). Both were replaced with a shorter natural word the icon disambiguates (`Mots`, `Карталар`) rather than an abbreviation, and rather than renaming all 11 locales to a shorter concept ("Words"), which would have fought the established in-bot term — the dictionary screen is headed `📖 Your Dictionary` and a user can have several named dictionaries. All 33 labels now fit one row down to 360dp; the budget is documented on `buildMainKeyboard` for future translations. The commands themselves still work when typed — only the advertisement moved. Taps arrive as plain text, so `bot.hears(mainMenuLabels())` is registered **ahead of `modeRouterMiddleware`**, or translate mode would have tried to translate the button label; matching covers the labels in **every** supported language, because the keyboard Telegram shows is whatever was last sent and survives an interface-language switch. Delivery is handled by `mainKeyboardMiddleware` + a `mainKeyboardVersion` flag on the Postgres-backed session: `/start` installs the keyboard directly, and any user who onboarded before it existed gets it once, with a one-time hint (`mainMenuHint`), on their next message — without it they would have lost the three commands from the menu and never received the replacement. Bumping `MAIN_KEYBOARD_VERSION` re-delivers a changed layout to everyone exactly once. Because a button *is* one of these commands, taps are treated as external actions on the same footing: `exitActiveConversations` abandons an open dialog for a main-menu tap exactly as it does for a typed command, and the report-issue description wait rejects them (alongside the `/`-prefix rejection it already had) so tapping 📖 Dictionary mid-report opens the dictionary instead of being filed as the bug description. New i18n keys `menuBtnDictionary`, `menuBtnFlashcards`, `menuBtnVideos`, `mainMenuHint` in all 11 locales; `welcomeBack`'s command list also gained the matching icons. Covered by tests for keyboard rendering/persistence, label matching across all locales (including that an ordinary word like "dictionary" is *not* matched), the one-time delivery and version bump, and that the moved commands are absent from `getLocalizedCommands`.
- **Timeout notices now carry a "🔄 Try again" button.** When a translation or a mentor turn died on a user-facing timeout, the bot replied with a dead-end notice ("⌛ This is taking longer than expected. Please try again.") and the only way to act on it was to retype the input. The notice now ships an inline retry button that re-runs the exact same request — including the context hint, which is re-encoded through the `word :: hint` freeform syntax so a callback update (which carries no message entities) reproduces it. Tapping acks the callback, deletes the notice so a double tap cannot launch two paid AI calls, and restarts the flow from its entry point (quota, model, and language detection all re-resolve, as if the user had retyped). Hard, non-transient failures keep the plain error text — retrying those would only fail the same way. The payload lives in the session keyed by the notice's message id (Telegram's 64-byte `callback_data` cap cannot hold the input), is one-shot, and is capped at 5 entries; a button that outlives its entry answers "session expired" and drops itself. New `retryButton` string in all 11 interface languages.
- **D+1 activation nudge: one message to users who finished onboarding and then never translated anything (Task 72, slice 8).** A daily in-process cron (09:40 UTC — clear of the 03:15 telemetry-retention sweep and of the notification scheduler's on-the-hour windows, mirroring `retention.wiring.ts`) finds users who completed onboarding at least 24 hours ago, are still active, have **zero** rows in `translation_requests` since completion, and have never been nudged — then sends them one message built from a curated hook word for one of their learning languages plus a **Show me the card** button that renders the cached demo card with no AI call. It is a one-off, never a series: the delivery is written to `notification_history` under the shared `onboarding_nudge` source, and the eligibility query excludes anyone who already has such a row. The record is written **after** a successful send, so a Telegram failure leaves the user eligible for the next sweep rather than silently consuming their single nudge, and one failed send never aborts the rest of the batch. Answering "has this user translated since finishing?" needs an instant onboarding actually finished at, so `users.onboarded_at` is new (migration `0047_greedy_senator_kelly`, one nullable column) and `markOnboarded` now writes it; rows completed before the column existed carry `NULL` and are deliberately treated as **not** eligible — their D+1 window is unknowable and nudging months-old accounts would be spam. Both exclusions are correlated `NOT EXISTS` subqueries in a single Drizzle query (never a per-user round trip), the sweep is capped at 500 users with a warning when the cap truncates a batch, and outcomes are counted on `bot_notifications_total` with a bounded status label. The nudge button uses its own `nudge:card:` callback prefix rather than `onb:` — every recipient is by definition already onboarded, and the onboarding handlers deliberately ignore those taps, which would have made the button silently dead. Covered by sweep behaviour tests (fires once and records it, sends nothing on a second sweep, a failed send records nothing and does not abort the batch, a user with no curated hook word is skipped) and by real-Postgres integration tests proving the eligibility SQL itself: the already-translated and already-nudged users are excluded, a pre-onboarding translation and an unrelated `notification_history` source are not, and neither a sub-24-hour nor a `NULL onboarded_at` user is ever selected.
- **Onboarding redesigned around a real translation card in three screens, and moved out of the grammY conversation entirely (Task 72).** The old flow asked for a native language (10 buttons, one per row), then learning languages (9 more, one per row), then a **separate full screen of CEFR levels per learning language**, and finally asked the user to type a word — whose "translation" was the static `demoResult` placeholder *"(AI translation will appear here once connected)"*. Worst case that was 7 screens and ~11 taps for a fake payoff. It is now: **screen 0** states what the product does and puts every supported language on one screen, with the one guessed from `ctx.from.language_code` promoted to its own row reading "✅ 🇬🇧 English — I'm a native speaker" rather than a bare Yes (there is no "another language" step to find, and the guess is only a hint — `language_code` reports the *Telegram app's interface language*, which for an expat or anyone with an English phone is not their mother tongue; the prompt also names the consequence, "that's what I'll translate into", so a skimmer catches the mistake); **screen 1** takes learning languages *with* their level — tapping a language expands a compact `A1 A2 B1 B2 C1 C2` row **inside the same message** (the long "A1 — Beginner" labels that forced one button per row moved into the prompt text), and picking a level collapses it back to a `✅ 🇩🇪 Deutsch · B1` chip, so each extra language costs 2 taps and **zero** extra screens; **screen 2** renders a **real** card from a curated hook word (`🇩🇪 Backpfeifengesicht`) served from the `onboarding_demo_cards` cache with **no AI call on the tap path** — typing a word still works and runs the real pipeline with its normal typing indicator and progress message; **screen 3** closes with the usage instructions and inline buttons into the existing dictionary/practice/video/settings scenes instead of *"Use /translate"*. Happy path: `/start` → rendered card in **5 taps, no typing**. `🤷 I don't know` is a first-class answer on the level row and persists the `B1` column default, so it is indistinguishable downstream from an explicit B1; a language is added to `learningLangs` **only** when a level is chosen, so it can never be saved without one; re-tapping a confirmed language re-opens its row to change or remove it. A demo failure shows an apology and **still** completes onboarding rather than stranding the user. An optional screencast is sent above the final screen when `ONBOARDING_SCREENCAST_FILE_ID` holds a Telegram `file_id`; its absence is a normal state and a send failure is swallowed. `/settings` level editing is untouched.

  **Structurally**, onboarding no longer runs inside a grammY conversation (`onboarding.scene.ts` and `stale-onboarding.helper.ts` are deleted). It is a set of plain callback handlers that re-derive every screen from the database (`users.onboarding_step` + `user_language_settings` + `user_learning_languages`) on each update. That removes three production failure modes by construction rather than by mitigation: the 10-minute `maxMillisecondsToWait` timeout that left `lang:`/`learn:`/`level:` buttons permanently dead with zero errors logged (2026-08-01 incident) — a pause of any length is now invisible and `/start` resumes on the furthest screen reached instead of restarting from step 1; the abandoned dialog that swallowed every subsequent message until a restart (2026-07-06), which is why every `waitUntil` needed `{ next: true }` — an unrecognised update simply falls through the middleware chain now; and the replayed context whose `ctx.session` could be `undefined` and crashed completion after `markOnboarded` had already run. `exitActiveConversations`'s allowlist shrank to `report:`, the only conversation left. Every screen entry writes `users.onboarding_step` and the `bot_onboarding_step_total` counter, with the demo recording `hook_tapped`/`typed_word`/`failed` distinctly. New i18n keys across all 11 locales (real translations, not English copies); `demoResult` and `enterWord` are removed. Covered by 36 behaviour tests driving the real handlers against an in-memory repository, and 6 grammY e2e tests against a real Postgres asserting the 5-tap path reaches a cached card with the AI port left rejecting, that an unreviewed card is never served, that a failed demo still completes onboarding, and that a second `/start` mid-flow resumes rather than restarts.

- **Review pass on the Task 72 onboarding redesign closed ten defects found by a multi-agent code review.** The ones that would have hurt in production: onboarding **completed unconditionally** after any demo attempt, so a user who typed an ambiguous word got the "which meaning did you mean?" question instantly buried under the completion screen and was marked onboarded having never seen a card — completion is now gated on a card actually being rendered (`session.pendingCardMsgId` advancing), and the one case that still completes is a genuine pipeline failure, because `handleTranslateText` swallows its own errors and refusing to complete would have stranded every new user for the duration of a model outage. Taps on keyboards left over from the **old conversation flow** (`lang:` / `learn:` / `level:`) matched no handler at all after the migration, silently recreating the 2026-08-01 "bot stopped responding to language selection" incident for anyone mid-onboarding at deploy time; a recovery handler now puts them back on a live screen. `onboardingTextMiddleware` **swallowed mentor-mode free text** from a not-yet-onboarded user (no command is gated on `onboarded`, so `/mentor` is reachable mid-flow), which is the same swallowed-message class the module exists to remove. The **one-tap native-language guess was irreversible** — an expat on an `en-US` phone who tapped "✅ Yes, English" was locked into an English interface for the rest of setup — so the language screen gained a back button. A screen older than Telegram's 48-hour edit window falls back to a fresh message, and that replacement was **never tracked for cleanup**, leaving a dead-looking setup screen in the chat forever; `present()` now tracks it. The demo-card cache **could never be served**: `is_active` defaults to false and nothing in production could flip it, so every hook tap fell through to the live pipeline — there is now a **Demo Cards review page** in the admin panel (list with payloads, approve/un-approve, and a cached-vs-servable backlog counter) behind `GET /api/onboarding-demo-cards` and `PUT /api/onboarding-demo-cards/active`. the screencast's `ONBOARDING_SCREENCAST_FILE_ID` was read from `process.env` but never reached the bot container, so it could never have appeared — and since its absence is by design not an error, the misconfiguration was silent. It is now a plain constant in `apps/bot/src/constants.ts`: a Telegram `file_id` is not a secret, never changes once the asset is uploaded, and does not vary between environments, so routing it through `.env` → compose → a CI secret was three moving parts for one opaque string that would still have needed a deploy to change. The D+1 nudge retried a **blocked user every day forever** (a permanent 403 was treated as retryable); permanent failures — 403 and `chat not found` — are now classified by a shared `isUserBlocked` / `isPermanentDeliveryFailure` helper lifted out of the notification scheduler, and retire the user by spending their history row. The nudge also had **no upper age bound**, so it was not a D+1 nudge at all; the window is now 24–72 h, deliberately wider than the daily cadence so a missed sweep cannot skip a cohort. Finally, the new review listing counted rows with `sql<number>\`count(*)\`` — an assertion, not a conversion, so Postgres' bigint arrived as the *string* `"3"` and every numeric comparison against it silently failed; both count paths now coerce. *Not changed:* the nudge deliberately does **not** filter on `notification_enabled`. That column defaults to false and governs the recurring reminders users opt *into*, so filtering on it would have excluded nearly every user and quietly reduced the sweep to a no-op; a blocked user is retired on their first failed send instead.

- **Curated onboarding hook words and their card cache (Task 72, slice 4).** The onboarding demo can now be instant instead of an AI call the new user waits on. Three headwords per supported learning language (all 11: en, ru, cs, de, fr, es, it, pt, uk, pl, kk) live in code as the source of truth (`packages/core/src/modules/onboarding/hook-words.ts`), each picked to show what a plain dictionary cannot — an untranslatable concept (de `Backpfeifengesicht`, es `sobremesa`, cs `prozvonit`, pt `saudade`), an idiom whose literal reading breaks (en `it's not my cup of tea`, fr `avoir le cafard`, it `in bocca al lupo`), or a quirk of the language itself (de `doch`, fr `si`, pl `no`, cs `strč prst skrz krk`) — under the spec's curation constraints (no vulgarity, no politics, no culturally loaded jokes, and the point must survive translation into every interface language). The new `onboarding_demo_cards` table (migration `0046_strange_killer_shrike`) caches the rendered `TranslateOutput` per `(source_lang, native_lang, headword)`, and `onboardingDemoCardRepository` serves **only** reviewed rows: both `findActive` and `findOne` filter on `is_active = true`, so an unreviewed card can never reach a user. `upsert` refreshes the payload and the keyboard ordering on conflict and deliberately never writes `is_active` — regenerating a card cannot publish it behind the manual review step. A warm-up script (`pnpm demo-cards:warm [--force]`) generates the cards for `native ∈ {ru, en, cs}` × every learning language through the **real** translation pipeline, skipping triples it has already cached unless forced, and exits non-zero if any card failed. Covered by hook-list behaviour tests, repository unit tests, and real-Postgres integration tests in the Task 71 lane (the `is_active` filter and the unique-index upsert are proven against the database, not a mock).

- **Onboarding drop-off is now measurable (Task 72, slice 1).** Onboarding recorded a step only for the first two screens, so a user who abandoned on the level screen and one who abandoned on the demo were indistinguishable — the redesign could not be evaluated. This ships the instrumentation primitives: a shared step/outcome vocabulary (`ONBOARDING_STEPS` 1–4, `ONBOARDING_OUTCOMES` `entered`/`hook_tapped`/`typed_word`/`failed`/`completed`) plus a `bot_onboarding_step_total{step,outcome}` Prometheus counter with a deliberately bounded label space, a `getOnboardingFunnel()` query grouping users by furthest step reached and completion, the `GET /stats/onboarding-funnel` admin-api endpoint, and an **Onboarding Funnel** panel on the admin Request Stats page showing per-step user counts with the onboarded / not-onboarded split and an overall completion rate. `markOnboarded` now writes step **4** (the new "complete" screen); rows completed under the previous 3-screen flow keep `3` and are not backfilled, so the funnel splits on `onboarded` rather than on the step alone.

- **Post-translation "Clarify meaning" now sends a new card instead of editing the previous one in place.** Adding clarifying context to a rendered card (the 🎯 Clarify meaning button followed by a context message) re-translated correctly but rewrote the original card via `editMessageText`, discarding the pre-clarification result and failing on cards past Telegram's 48-hour edit window. The clarified translation is now posted as a **new** card, leaving the previous one as a snapshot; any accumulated "Other meaning" history is preserved on the new card and the pending-card pointers advance to it. Covered by a test asserting a new card is sent and the previous card is never edited in place.

- **"Other meaning" now sends a new card instead of editing the previous one in place.** Tapping 🔄 Other meaning previously rewrote the existing translation card via `editMessageText`, which discarded the prior sense and failed outright on cards older than Telegram's 48-hour edit window ("message to edit not found"). It now posts the alternative sense as a **new** card and leaves the previous card untouched as a snapshot, so every sense stays visible and old cards keep working. The accumulated negative constraints are carried forward into the new card's session entry, so a further tap still excludes every sense already shown; the pending-card pointers advance to the newest card. Covered by a new append-not-edit test (new card sent, previous card never edited in place, history carried forward, and no-more-meanings leaves the previous card untouched).

- **Doubtful source-language override: a "translate from" flag menu on the rare cards where detection had to guess.** When the source language cannot be resolved confidently and the pipeline falls back to a heuristic guess (the two fallback branches in `handleTranslateText` — a detected-but-out-of-set language, or weak shared-script ambiguity), the translation is still shown, but its card now carries an extra keyboard section: a non-actionable "🌐 Wrong language? Translate from:" header plus one flag button per candidate language (the user's native + learning set, minus the guessed source), `tr:srclang:<code>:<mid>`. Tapping a flag re-translates the *same* original text with that language forced as the source hint and emits a **new** card (via the existing mistype-confirm pipeline), leaving the doubtful card in place as a snapshot; the forced-source retranslation is never itself doubtful, so the menu cannot loop. The menu is **rare by construction** — it is gated on the heuristic-fallback branches only, never on the common confident-detection path (and not on target-side quality signals like `needs_review`, which are orthogonal to source-language doubt). Two advisory telemetry events (`override_shown`, `override_used`) are recorded to `language_detection_events` (free-form `text` column — no migration; the port and adapter `eventType` unions were widened) so the trigger's precision can be measured and tuned. New i18n key `translationSourceFromLabel` (en + ru; other locales fall back to English). Covered by renderer keyboard tests, an end-to-end gate test (doubtful path attaches the menu + records `override_shown`; confident path does neither), and handler tests for the override callback including the null-direction guard.

- **Real-DB integration test lane on free throwaway Postgres, with an optional Neon-branch mode (Task 71 v2).** A second Vitest lane (`pnpm test:integration`, `*.integration.test.ts`) runs against a real, migrated **and seeded** Postgres, so bugs mocks structurally cannot catch (LIKE escaping, pagination ordering, unique-constraint upserts, the `languages` data-seed, real grammY dispatch) are covered; the base `pnpm test` stays fast and mock-only. **Cost model:** the CI job (`ci.yml` `integration`, push/PR to develop and master; still gating master deploys via `deploy.yml`'s `workflow_call`) uses a **runner-local `services: postgres:17` container** — a brand-new empty database per run, destroyed with the job, zero secrets, **zero Neon compute-hours**; the Neon ephemeral-branch lane (pinned `neonctl`, branch from `ci-base`, trap-guaranteed delete, `pnpm neon:prune` sweeper) remains available locally behind `NEON_API_KEY`/`NEON_PROJECT_ID`. Provisioning order everywhere is the prod path: `db:migrate` (includes the languages seed) then `pnpm admin:seed` (plans + feature access). v1 coverage recovered from the July stash and reconciled with a month of develop drift: user/vocabulary/bot-session repository tests, a grammY e2e harness (onboarding, translate happy path, session/callback regressions) with the AI boundary mocked via DI, plus a new **fresh-DB bootstrap test** asserting the minimal base configuration (46 `languages` rows/11 supported, `free` default plan, paid-plan feature access) a re-created database needs before users can use the bot (documented in `@docs/tasks/71-neon-integration-tests-ci.md`). Harness fixes over v1: outbound Telegram calls are intercepted at the **fetch level** (the conversations plugin's cloned Api bypasses api-transformer mocks — onboarding replies would have escaped to the real API), synthetic `/commands` now carry the `bot_command` entity grammY actually matches on, and the flood-limit throttler is stubbed in this lane (CI `node-version` also bumped 24→26 for prod parity).

### Fixed

- **The persistent menu under the input field vanished after a single translation, and the commands it replaced were no longer in the command list — leaving the dictionary, flash cards and videos unreachable.** Telegram binds a reply keyboard to the message that delivered it: delete that message and the menu goes with it. Both places that installed the keyboard — the one-time hint in `mainKeyboardMiddleware` and `/start`'s greeting — registered their message with `trackTechnicalMessage`, and `cleanupTechnicalMessages` runs at the top of **every** translation (plus the settings, dictionary, flash-card, SRS and template flows). So the menu survived until the user's next message and then disappeared, permanently: `mainKeyboardVersion` was already stored, so it was never re-sent. The carrier message is no longer tracked for cleanup (`installMainKeyboard` is now the single place that sends it, and it records `mainKeyboardMessageId` in the session); should anything sweep the carrier up anyway, cleanup clears the delivery flag so the middleware re-installs the keyboard on the next message instead of leaving the chat without a menu. `MAIN_KEYBOARD_VERSION` is bumped to `2` so every user whose keyboard was already deleted gets it back once. The version flag is now written **after** Telegram accepts the send, so a failed send retries rather than marking the chat done. `/dictionary`, `/flashcard` and `/videos` also return to the Telegram command list (same icons as their buttons): a reply keyboard lives only as long as its message, so clearing the chat history still took the features away with no path back — the command menu is the one that survives. Covered by unit tests on the carrier not being tracked and on cleanup re-arming delivery, and by a real-dispatcher e2e test proving the keyboard survives two consecutive translations and is not re-sent.
- **A freshly provisioned database had no AI model at all, so every AI call failed on it — including the whole CI integration lane.** Making model ids database-only removed the last hardcoded slug, which also removed the only thing that made an *empty* `ai_models` table work: with no plan model, no default and no fallback, `resolveDefaultAIModel` throws `AIModelNotConfiguredError`, and nothing ever wrote a first row. The existing dev and production databases carry a model, so the gap was invisible there and surfaced on the one database that is genuinely new on every run — CI's throwaway Postgres, where the translate-flow and callback-regression e2e tests started failing on `AIModelNotConfiguredError` in middleware. A fresh **deployment** had the same bug and a worse symptom: the bot would have answered nothing at all until an admin opened the AI Models page. The bootstrap seed (`pnpm admin:seed`, already the step that creates plans and feature access) now also gives an empty catalog one enabled default model. It is guarded on the table being **empty** rather than upserted per row, because this seed re-runs on every production deploy and — unlike plans — the catalog and its default/fallback roles are admin-owned state that a release must not reset; no fallback is flagged, since with a single model a failover split would only re-target the model that just failed. The fresh-DB bootstrap spec, whose header had explicitly excluded `ai_models` on the now-obsolete grounds that "code falls back to hardcoded defaults when they are empty", asserts the default model alongside languages, plans and feature access.

- **The onboarding 🎬 Video button led straight into a dead end, and trying the feature cost a third of the free plan.** The empty state was a bare "No videos processed yet. Send a YouTube link!" — which never says what *kind* of video works, offered to a user who has just finished setup and has processed nothing. It now leads with curated starter videos for the languages that user actually studies (`packages/core/src/modules/onboarding/video-suggestions.ts`, round-robin across their learning languages, capped at four buttons), falling back to the plain invitation when none of their languages has a verified pick — better an honest empty screen than a suggestion in a language they are not learning. - **A single false-positive from one low-confidence validator rule no longer forces an otherwise-good translation into `needs_review`.** Production logs showed most weekly "quality failures" were false alarms, and the biggest single driver was the single-word first-example check (`example.validator.ts`): it demands the card's first example demonstrate the headword, but its stem matcher over-rejects correct inflected core vocabulary (de `anrufen`, pl `iść`, kk `бару`, ru `спать`, it `essere`). So a false blocking hit on a high-risk word simultaneously rejected a good card and switched off the only real semantic gate. The single-word first-example check now reports a distinct rule (`first-example`) that the service maps to a new **`advisory`** severity: it is recorded but non-blocking, so it never forces `needs_review`, never triggers repair, and — the point — no longer suppresses the semantic judge, which now runs on a high-risk word whose only deterministic issue is this advisory one and provides the true retention gate (a real meaning error, e.g. cs «Auto se courá» → «машина сломалась», is still caught by the judge and routed to `needs_review`). Everything else — the multi-word "at least half", no-examples, empty-target, field-language, semantic, immutable, duplication, and judge-timeout rules — stays blocking. Advisory issues are counted like `info` (i.e. not as failures) by the translation benchmark, and `finalizeStep` now emits a distinct info line when a card is accepted with advisory issues so the two outcomes are separable in logs. The risk scorer was also tightened to count only *blocking* validation issues, so an advisory issue neither manufactures risk nor, via the blocking-gate, mutes the judge (behaviour-preserving for all prior cases, which only ever produced blocking issues).

- **Choosing "add context" on a translation clarification no longer breaks with "⚠️ Something went wrong" (and no longer poisons the next translations).** Reported on the unrecognized word «Dabihga»: the bot asked for clarification, the user picked "add context" and typed a hint, and every attempt from that point surfaced the generic error. - **Multi-word translations must now actually be demonstrated by their examples — idiom cards could teach one expression and illustrate it with three others.** Reported on the Russian idiom «какать кирпичами»: the English block gave the correct headword `to shit bricks` but then illustrated it with "scared stiff" and "petrified", and the Czech block put `kadit cihly` — a word-for-word calque no Czech speaker uses — in the headword while its own examples used the genuine idioms (`podělaný`, `nahnáno`). Nothing caught either defect, for two independent reasons: `validateExamples` only ever inspected `examples[0]`, and it skipped the headword check **entirely** when `expressionType === "idiomatic_equivalent"` — so an idiom card received zero example validation. For a translation of **two or more significant tokens**, the check now runs on every example and every expression type, and requires at least half of them to demonstrate the translation. "At least half" rather than "all" is deliberate: a functional equivalent may legitimately be paraphrased once, and matching stays per-token by stem, so inflection, reordering, and dropped function words still pass (the `der Spott, -e` and `etwas auf dem Kasten haben` regression fixtures are unchanged). **Single-word translations deliberately keep the old first-example rule**, because extending coverage to them was measured to reject large classes of correct output — `sameStem` needs an exact match below 5 characters and a shared 4-character prefix above it, so de `anrufen` scored 0/3 (the separable prefix splits off in every finite clause), pl `iść` 0/3, kk `бару` 0/3, ru `спать` 1/3, it `essere` 1/3. That is core vocabulary, and every validation error is `severity: "blocking"`, so shipping that would have re-run the over-strictness incident that once pushed ~36% of translations into `needs_review`; fixing it needs real stemming rather than a wider threshold. The error is anchored to the first failing example's index so repair gets a concrete location, and the `examples` repair instruction was reworded — it previously said "make **each** example use the assigned translation", which both contradicted the at-least-half rule and pushed the model to rewrite good examples around a wrong headword. Two prompt rules back this up (`prompt.builder.ts`): the idiomatic rule now states that a calque no native speaker says is a **wrong** answer and that a language with no established idiom must get natural plain wording rather than a manufactured one, and the examples rule requires at least 2 of 3 sentences to use `text` rather than a synonym. Two pre-existing tests asserted the old skip behaviour — that idiomatic examples which never demonstrate the idiom should pass — and were inverted, since that is the defect itself. Benchmark: a new `idiom-kakat-kirpichami` fixture pins the reported case, and three previously assertion-less idiom fixtures (`break-a-leg`, `delo-v-shlyape`, `byty-baydyky`) gained deterministic `forbiddenSubstrings` guards. Note that benchmark substring assertions only inspect `translations.<lang>.text`, so example drift surfaces there indirectly, as a `needs_review` status. The Czech judgement that `kadit cihly` is not an attested form is an editorial call recorded in a comment beside the fixture and is worth reconfirming against a corpus. **Not fixed here:** a calqued headword that the model then uses consistently across all three examples still passes, since nothing deterministic can tell an invented idiom from a real one — that is a knowledge question for the semantic judge. An attempt to infer the real expression from the words the failing examples share was implemented and then removed: every cheap heuristic for it reassembles function words into phrases nobody said (`"было очень"`, `"that when"`), and quoting those back as the expression natives supposedly use would corrupt a headword that was merely mis-illustrated.

When the primary model timed out, the failover attempt therefore errored out in milliseconds instead of recovering, turning a merely slow request into a failed one. - **Russian translations that quote a foreign word are no longer wrongly flagged as "wrong language", which was the single biggest driver of slow translations and `needs_review`.** The `field-language` validator required a Russian field to be at least half Cyrillic (and to contain at least two Cyrillic characters). A perfectly good short Russian gloss or example that quotes the English head-word — explaining "thus", "seam", "dimmed", "crutch", "prescient", an annotated German noun, or a multi-word idiom — tips that ratio over the line purely because the quoted word is in Latin script. The false failure then triggered a full AI repair round, so some words burned up to four AI calls and *still* landed in `needs_review`. The rule now flags a field only when it is genuine romanization: no Cyrillic at all, or a Cyrillic share below 15% of letters. Both halves of the corpus ship as permanent regression fixtures: the quoted-foreign-word cases must pass, and true romanization such as "privet, kak dela" must still fail. - **Source-language usage examples no longer intermittently collapse to the bare headword.** For a learning-language source word (e.g. English "nevertheless" for a Russian speaker), the `sourceUsage.examples` block is meant to show full source-language sentences using the word, each with a native translation. Because the instruction was ambiguous rather than structurally wrong, the model resolved it **non-deterministically** — sometimes putting the full source sentence in `"target"` (correct), sometimes collapsing it to the bare headword and pushing the whole sentence into `"native"` — rendering as `💬 nevertheless (Погода была холодной; тем не менее…)` instead of `💬 The weather was cold; nevertheless, we went for a walk. - **Semantic judge no longer rejects the translation's own output schema.** The high-risk semantic-judge prompt (`buildJudgePrompt` in `packages/core/src/modules/translation/translation.service.ts`) told the model to flag "target text polluted with emoji, labels, explanations, or metadata that were not in the source". ### Added

- **Per-phase translation latency metrics — you can now see *where* a slow translation spends its time.** Until now the only signal was `bot_translation_duration_seconds`, a single number for the whole request, so a regression could be observed but not localized. The new `bot_translation_phase_duration_seconds{phase}` histogram (`apps/bot/src/metrics.ts`) breaks the path into seven phases: `pre_ai` (settings, input validation, direction resolution, quota), `detection` (the sync language pass plus any AI escalation), `preflight` (the ambiguity-checking AI round-trip that runs when detection was too weak to skip it), `generate`, `validate` (deterministic validation and targeted repair), `judge` (the semantic judge and its repair-and-re-judge cycle), and `post_ai` (the duplicate-lookup SELECTs and the Telegram round-trips that render the card). A phase that did no work on a given request is **not observed at all** rather than recorded as zero — `preflight` short-circuits on confident detection and `judge` only runs on high-risk input, so emitting zeros would drag those quantiles toward zero and hide the very tail the metric exists to expose. The phases are not an exhaustive partition of the total: the dictionary context lookup carries no label of its own, which the metric's own documentation now states rather than leaving a reader to discover it by subtraction. Cardinality is bounded by construction — a single `phase` label drawn from a fixed, type-constrained set, with no user/word/model dimension. Three of those phases run inside the pure-core pipeline and were previously unmeasurable from the bot; rather than estimate them, core now reports its own timings through an optional `onPhase` sink on `ContextEnrichmentDeps` (`TranslationHooks`). Core stays pure — it emits numbers into whatever sink it is handed and knows nothing about Prometheus, an absent sink is a no-op, and a throwing observer is logged and ignored rather than breaking a translation. The bot deliberately does **not** also time `generate` itself, which would double-count it; a test pins that. `bot_translation_duration_seconds` and its buckets are unchanged.
- **Translation-benchmark expansion to all 11 menu languages.** `apps/translation-benchmark` grew from 31 to **49 translation-quality scenarios** and from 72 to **89 source-language detection scenarios**, so every menu language (en, ru, cs, de, fr, es, it, pt, uk, pl, kk) is now exercised as a source or target — previously fr, it, pt, uk, pl, and kk had no translation coverage. The new translation fixtures are drawn from verified linguistic sources (Wikibooks *False Friends of the Slavist*, Wiktionary, the ACES/WinoMT/ContraPro MT challenge-set literature, and the KRCS Kazakh–Russian code-switching corpus) and add categories for **false friends** (antonym-flip traps like pl `zapomnieć`→ru "запомнить", cs `čerstvý`→ru "чёрствый", uk `неділя`→ru "неделя", it `burro`→es "burro", pt `esquisito`→es "exquisito"), **idioms** for fr/it/pt/pl/uk/kk (e.g. "poser un lapin", "in bocca al lupo", "pagar o pato", "не мій цирк", "бити байдики", "қой аузынан шөп алмас"), **pronoun-gender anaphora** ("The doctor asked the nurse to help her"), **number preservation**, and **long German compounds**. Deterministic assertions (`immutableTokens`, `forbiddenSubstrings`) guard the token/antonym traps; gender/register/compound cases are judge-scored. The new detection fixtures add **kk↔ru** ambiguity (shared-Cyrillic words like "он"/"бар" and "Он бала бар" → ask; unique Kazakh letters ә/қ/ң/ұ/і → kk), **pl↔cs** close-language pairs, four-language homographs ("come" en/it/es/pt, "sale" en/fr/it/es, "sole", "dice"), and a Ukrainian-unique-letter case. Data-only change: the benchmark runner contract, report schema, and product translation code are untouched.
- **Self-healing Phase 2 — AI fallback-model failover with a fixed budget split.** A **quality upgrade, not a freeze fix**: the AI adapter's per-request `AbortController` already bounds a hung provider to the request budget and surfaces a graceful `AITimeoutError` (Phase 1 / earlier work). Phase 2 *upgrades* that surfaced error — or a transient provider failure (**429**, **5xx**: 408/429/500/502/503/504, or an abort/timeout/network fault) — into a **successful reply on a second model** instead of a user-facing error. The split is **fixed up front**, replacing the earlier shared-remaining-budget idea (which was theatre): with the default request budget `B = clampAiBudgetToOpGuard(requestTimeoutMs) = 15_000`, the primary attempt runs bounded by `primaryBudgetMs = B − reservedFallbackMs = 10_000` and, on a retriable failure, the fallback model runs bounded by `reservedFallbackMs = 5_000`, so **both attempts together fit inside the 20 s op guard** (the `B` clamp *ceiling* is ~18_000, reached only if an admin raises the budget; 18_000 is never a hardcoded default). New `packages/adapters/ai/src/failover.ts` exposes `withModelFailover({ primaryModel, fallbackModel, primaryBudgetMs, reservedFallbackMs }, call)`: it runs `call(primary, { budgetMs: primaryBudgetMs })`; on a **retriable** error it runs `call(fallback, { budgetMs: reservedFallbackMs })` and emits an `AIFallbackEvent`; on a **non-retriable** error (4xx / validation / schema) it **rethrows immediately with no fallback** so real bugs are never masked. **N2 dedup:** when `primaryModel === fallbackModel` (e.g. the admin left the DB default null, so both resolve to the hardcoded `FALLBACK_AI_MODEL`) the primary runs **exactly once** with no second attempt and no metric. Budget-injection plumbing (**N1a**): `GenerateOptions` gains an optional `budgetMs` that overrides the adapter's self-resolved request budget for a single attempt (unchanged when omitted), threaded through `withInstrumentedCall`; `generateObject`/`generateText`/`generateChat` route through `withModelFailover` only when an `options.failover` config is supplied, and lower the primary attempt's AI-SDK `maxRetries` to 1 (the fallback model *is* the retry strategy). Wiring: the composition root (`apps/bot/src/container.ts`) wraps `ctx.services.ai` so **every** bot AI call gets failover — the per-call `model` is the primary (resolved from `getDefaultAIModel()`/`getDefaultAIModelForPlan()`), the hardcoded `FALLBACK_AI_MODEL` (`apps/bot/src/utils/ai-model.ts`) is the fallback, and the split is derived from the same admin-managed budget the abort timeout uses (`buildAiFailover(B)`); no DB/schema change. A new bounded-cardinality Prometheus counter **`bot_ai_fallback_total{from_model, to_model, reason}`** (`apps/bot/src/metrics.ts`) counts failovers, fed via a DI observer (`setAIFallbackObserver`, same pattern as the metric sink). The stale compiled artifact `apps/bot/dist/utils/ai-fallback.js` (an older port-decorator design with no matching source) was deleted. Load-bearing test: a fake-timer wall-clock proof that a hung primary is aborted at `primaryBudgetMs` and both attempts fit inside `B` — verified to go **red** on a double-full-budget implementation.
- **Self-healing Phase 3 — per-model circuit breaker gating the AI failover path.** Adds a pure per-model circuit breaker in front of the Phase 2 failover so a provider that is already failing is fast-failed instead of hammered with more doomed requests (the direct successor to the 2026-07-01 model-freeze incident). New dependency-free `packages/core/src/resilience/circuit-breaker.ts` (`CircuitBreaker`) implements `closed → open → half-open → (closed | open)` with an **injected clock** (`now`, default `Date.now`) for deterministic tests and an optional `onTransition(to)` callback so the pure module never imports a metric; config is `{ failureThreshold, cooldownMs, halfOpenProbes }`. `packages/core/src/resilience/breaker-registry.ts` lazily creates + caches one breaker per model id (`getBreaker(modelId)`), isolating model A's health from model B, with defaults **failureThreshold 5, cooldownMs 30_000, halfOpenProbes 1**, a `resetBreakerRegistry()` for test isolation, and a parallel DI observer `setAICircuitObserver({model, state})` fanning transitions out to the composition root. Both are re-exported through the established single entry point `@polyglot/core` (**deliberate deviation from the plan's dedicated-subpath idea** — the whole repo, including the recent NaN fix, exports this way and there are zero subpath imports, so a bespoke `exports` map would be the only inconsistent one). The gate lives in `withModelFailover` (`packages/adapters/ai/src/failover.ts`): when enabled it `canProceed()`-checks the primary breaker (skip-if-open), records success/**retriable**-failure per model (a non-retriable 4xx/validation error **never** trips the breaker or is masked), routes to the fallback when the primary is open or failed retriably, and throws a typed **`AICircuitOpenError`** (`@polyglot/core`) with **no provider call** when the relevant breaker(s) are open — surfaced to the user as the graceful "⌛ …try again" notice via `isUserFacingTimeout` (`apps/bot/src/utils/long-op.ts`) and `apps/bot/src/bot-error-handler.ts`, never a raw error. It is **default-closed and behavior-neutral**: with both breakers closed (the steady state) it makes the exact same calls/budgets/results as Phase 2 (proven by a happy-path-neutrality test comparing gated vs ungated call traces). An env **kill-switch `AI_CIRCUIT_BREAKER_ENABLED`** (default ON, wired in `apps/bot/src/container.ts` via `setAICircuitBreakerEnabled`) disables the gate entirely — the redeploy-free rollback path (verified: an open breaker is ignored when off). Metrics: `bot_ai_circuit_state{model}` gauge (0=closed/1=half-open/2=open) and `bot_ai_circuit_transitions_total{model,to_state}` counter (`apps/bot/src/metrics.ts`), driven by the circuit observer. - **Self-healing Phase 1a — `/livez` "stuck-or-dead" liveness endpoint** on the bot's metrics server (`apps/bot/src/metrics.ts`), a third health signal alongside the always-ok `/healthz` (both left unchanged) and the deploy-gate `/readyz`. `/livez` is threshold-free and returns **503** only on the one unambiguous crash signal an autoheal restart can actually fix: a **silently-dead grammY runner** — the runner handle is set, we are not shutting down, yet `RunnerHandle.isRunning()` reports `false` (poller stopped, process alive). Liveness is deliberately **DB-independent** — probing the database here would keep Neon serverless Postgres awake around the clock instead of letting it auto-suspend between scheduler ticks, and a cold-DB probe right after a suspend could trip autoheal into a restart loop that cannot fix a suspended DB; DB health is checked separately by `/readyz`. Everything else is **200**: an idle-but-running bot (there is deliberately **no** staleness/latency/in-flight threshold — the un-guarded AI repair path scales with language count, so no fixed budget is safe), a graceful shutdown (a stopping runner must not read as a crash), and — critically — the **booting** window before the runner handle exists (a null-guard that never dereferences null, so startup can't 500). A wedged event loop needs no code: the HTTP probe simply times out. New leaf module `apps/bot/src/liveness-state.ts` holds the raw signals (nullable runner handle, shutting-down flag) and imports nothing from health/metrics/index/shutdown so it can't close an import cycle; `checkLiveness()` lives in `apps/bot/src/health.ts`. The runner handle is published right after `run(bot)` in `index.ts`, and graceful shutdown flips the shutting-down flag at the very start of its sequence (before stopping the runner). ### Changed

- **The post-generation AI tail is now bounded, so a pathological translation degrades gracefully instead of running until the hard timeout.** After generation the pipeline runs deterministic validation, targeted per-language repair, a whole-batch retry, a semantic judge, and a judge repair-and-re-judge cycle — none of which had any notion of how long the waiting user had left, because the translation pipeline had **no budget concept at all**. A single slow or repair-heavy word could therefore stack latency until the outer 20 s guard killed it and showed an error. `TranslateInput` now accepts an optional `deadlineAt` — an **absolute** timestamp rather than a duration, so core never re-anchors its own clock (an earlier duration-based draft was anchored after the dictionary lookup, which silently pushed the deadline past the outer guard and let a slow lookup eat the whole safety margin). The bot anchors it at the same instant it starts the outer `withTimeout` guard, using `TRANSLATION_BUDGET_MS` (`apps/bot/src/utils/long-op.ts`), deliberately set below that guard so the pipeline has room to wind down before the hard stop fires. Within that budget: the semantic judge runs under a time box and, on expiry, falls back to the already-validated pre-judge result — but **never ships it as a silently accepted card**. Because no semantic gate was obtained, the result is routed to `needs_review` through the existing finalize path (the judge only ever runs on high-risk inputs, so every judge timeout is by construction a high-risk one). A repair round is time-boxed to what remains **beyond** a reserved 4 s judge window — bounding what repair may *consume*, not merely whether it may *start*. (Gating only the start was not enough: a repair admitted with 4.5 s left could still run for the AI adapter's full ~10 s request timeout and eat the reservation outright.) So **the judge never degrades merely because repair spent the clock**. A judge that answers within its box keeps every correction it produced — only the clock falls back, and only ever to a result that already passed deterministic validation. **Absence of a budget is unbounded**, admitted through the same `isFinitePositive` guard that fixed the earlier "timed out after NaNms" outage: `undefined`/`NaN`/`Infinity`/`0`/negative all yield today's exact behavior with no timer created, so every other caller (batch/topic generation, tests) is untouched. **One behavior change on the failure path:** when a budget is supplied and is already spent, a generation error now propagates instead of triggering a whole-batch retry. That is the intended bound, but it does convert a would-be-retried failure into a hard failure under a tight budget.
- **Fewer redundant queries before a translation starts.** User settings were fetched uncached up to three times per Telegram update (auth middleware, mode router, and the translate flow itself); a request-scoped memo on `ctx` now resolves them once and shares the in-flight promise between readers. The memo records the user id it was resolved for and is ignored on mismatch, so the worst case degrades to a fresh query rather than to another user's settings, and grammY's per-update context means it cannot outlive one update. It is also explicitly invalidated after a settings write that is followed by another read in the same update — the "add this language" flow writes the new learning language and then re-enters the translation pipeline, which would otherwise still see the pre-write value and could offer to add the language the user had just added. Separately, the AI-model resolution and the user's translation-template lookup — which have no data dependency on each other — now run concurrently instead of serially. The duplicate-word lookup was deliberately **left sequential** and a comment records why: its second query consumes the first one's row id, so it is a genuine data dependency, not a missed parallelization.

### Fixed

- **Deliver scheduled notifications to users without a backfilled identity row** (Fable T24 review). T24 moved outbound Telegram chat-id resolution to the `identities` table exclusively, but migration `0044` creates that table without a backfill — so at deploy every existing user had no identity row, and their scheduled notifications were silently skipped (logged "skipping notification send" and returned). The dormant **re-engagement cohort** (`getInactiveUsers`) was hit hardest: it sends no inbound message, so it never self-healed an identity and would never receive its nudge. The outbound resolver (`resolveTelegramChatId` in `apps/bot/src/notifications/notification.wiring.ts`) now falls back to the retained legacy `users.telegram_id` column on an identity miss (new narrowly-scoped `userRepository.getTelegramIdById` channel-adapter read — the neutral `IdentityRepository` port stays channel-free) and opportunistically links an identity (idempotent `onConflictDoNothing`) so the row self-heals on that send. It only skips when **both** the identity and the legacy column are absent.
- **Close check-then-insert races and stop card regen wiping SRS progress** (Fable T18, findings E4/E8/E9). Several `select → insert` patterns had no unique-constraint backstop: (E4) a brand-new user's first messages/callbacks arrive concurrently, so two `findByTelegramId → create` calls could collide on the unique `telegram_id` and drop the first interaction — `userRepository.create` is now idempotent (`onConflictDoNothing` on `telegram_id` + re-select). (E8) `getOrCreateDefault` could insert a second default dictionary under a race — it now upserts via `onConflictDoNothing` on the unique `(user_id, name)` index + re-select; and `updateAllTranslations` used to **delete + re-insert** every translation on a full card regen, resetting each row's SRS schedule — it now **upserts** keyed on `(entry_id, target_lang_id)`, updating only content columns and leaving every `srs_*` column untouched (stale-language rows are pruned), so regenerating a card no longer wipes review progress. (E9) `logTranslationRequest` did three writes without a transaction — the request row and its target-language rows are now written atomically so a mid-write failure can't corrupt credit accounting. (Case-insensitive dictionary dedup and fully-atomic paid-tier rate limiting remain follow-ups needing a coordinated `original`/`word` normalization design shared with T04/T17.)
- **Index the `word_context` hot path — no more seq scan on every translation** (Fable T17, finding E2). Both the translation preflight (`context-lookup.ts`) and the single-word language sweep looked words up with `ILIKE(word, …)` (which a btree index can't serve) plus `arrayContains(forms, [word])` (which needs a GIN index — none existed), so on the kaikki dictionary dumps (hundreds of thousands to millions of rows) every message triggered a full table scan. The two hot lookups now use a case-insensitive **exact** match, `lower(word) = lower($1)`, backed by a new functional index `word_context_lower_word_idx` on `lower(word)`, and `arrayContains(forms, …)` is backed by a new **GIN** index `word_context_forms_gin_idx` (migration `0042`). Lowercasing is applied symmetrically on both sides so lookup results are unchanged; the admin partial-substring `search()` keeps its `ILIKE %…%`. (Full NFC write-side normalization, shared with the dictionary-dedup work, is a follow-up.)
- **Safe global bot error handler with a user reply** (Fable T15, finding B3). The old `bot.catch` only logged, and it read `ctx.session.activeMode` unconditionally — if a failure happened **before** the session middleware ran (in `update-metrics` or `sequentialize`), accessing `ctx.session` threw *inside the error handler*, producing an unhandled rejection in the runner; meanwhile the user was left staring at a frozen "Translating…". The handler (extracted to `apps/bot/src/bot-error-handler.ts`) now wraps its whole body in try/catch so it can never throw, reads `ctx.session` defensively, sends a **best-effort reply** (`genericError`, localized from the user's Telegram client language — no DB lookup in the error path) so no loader hangs, answers a pending callback to stop the button spinner, and classifies the cause as `telegram` (`GrammyError`) / `network` (`HttpError`) / `application` for the logs (aligned with T14). New i18n key `genericError` in all 11 locales.
- **Guard the admin AI-model controls against removing the model the bot depends on** (Fable T11, finding D2). `DELETE /ai-models/:id` would delete *any* model, including the current default, and `set-default` never checked that the target was enabled — either way the bot could be left pointing at a model it cannot call, falling back to a hardcoded id that may be unavailable (the same failure class as the `:free` 429 freeze). Deleting the current default now returns **409** ("Set another model as default first"), and setting a **disabled** model as default now returns **409** ("Enable it first"); a missing model still returns 404. The `logAiModelChange` audit log is unchanged. (A configurable fallback chain is tracked under T30/B15; the systemic move of the model/price source into the DB is T21.)

### Security

- **Long-tail low-risk cleanup — closed batch** (Fable T30, findings S6/B8/D6/S12/B12). A grab-bag of independent hardening fixes, each with a test. **(S6) Prompt-injection guards.** Free-form user text is interpolated into AI prompts, so a crafted message could try to hijack the model's instructions. The **mentor** system prompt (`packages/core/src/modules/mentor/prompt.builder.ts`) now carries an explicit rule that everything the user sends is untrusted learner input, never instructions — the model must ignore embedded commands/role-changes and stay in the mentor role (user text was already a separate `role:"user"` message, not concatenated into the system string). The **translation** prompt builders (`translation/prompt.builder.ts`, exported `USER_INPUT_INJECTION_GUARD`) now prefix both the main and metadata prompts with a guard that marks the interpolated word/phrase/sentence and any user context as untrusted content-to-translate, placed *before* the user text so the model reads it first. **(B8) Two-layer timeout invariant.** The bot's outer 20 s `withTimeout` op guard and the admin-managed AI request budget (DB `ai.defaults`, default 15 s) could disagree — an admin raising the budget above 20 s would leave the outer guard abandoning the await while the AI call kept spending on the owner's key. `clampAiBudgetToOpGuard` (`apps/bot/src/utils/long-op.ts`) now bounds the injected budget strictly below the outer guard (`LONG_OP_TIMEOUT_MS − AI_BUDGET_SAFETY_MARGIN_MS`, 2 s margin), wired at the composition root, so the adapter always aborts first and frees the socket/provider slot. **(D6) CORS + outbound fetch.** The admin-API CORS allow-list unconditionally added `localhost:4321` even in production; `resolveCorsOrigins` (`apps/admin-api/src/index.ts`) now adds the dev origin only when `NODE_ENV !== "production"`, so prod accepts only the configured admin origin(s). The two outbound OpenRouter proxy fetches (`routes/ai-models.ts`) gained a 10 s `AbortSignal.timeout` so a hung upstream can no longer hold an admin request open indefinitely. **(S12) ILIKE escaping.** User search terms were interpolated into `%…%` `ILIKE` patterns without escaping, so a literal `%`/`_` acted as a wildcard. - **Unified AI credit metering across all paid flows** (Fable T16, findings S1/S5 — economic DoS on the owner's OpenRouter key). - **RBAC + one unified auth hook — admin roles are now enforced** (Fable T07, finding S8). The JWT already carried a `role` (`superadmin`/`admin`) but **no route ever checked it**, so any active admin could delete AI models, delete tariff plans, or change users' subscription plans; meanwhile the `authenticate` decorator was dead code and all 11 route groups copy-pasted their own `onRequest` `jwtVerify` hook. - **Runtime revocation of admin access — deactivated admins lose access immediately, not in 24h** (Fable T06, finding S4). `isActive` was checked **only at login**; every other route and `/me` did a bare `jwtVerify`, so a blocked or deleted admin kept full access until their 24h token expired (no blacklist, no `tokenVersion`, no secret rotation). - **Global error handler + query-parameter validation on the admin API** (Fable T08, findings S9/D5). ### Fixed

- **Re-saving a word you previously deleted no longer crashes** (Fable T04, findings C2/E1). Deleting a word from a notification is a soft-delete (the row stays with `is_active = false`), but the duplicate check (`findByOriginalAndSource`) only looks at active rows, so a re-save found nothing and inserted — colliding with the `(user_id, original, source_lang_id)` unique index and throwing an unhandled `23505`. `vocabularyRepository.create` now **reactivates** the existing row via a race-safe `ON CONFLICT DO UPDATE` (on the entry's unique key and each translation's `(entry_id, target_lang_id)` key): the entry and its translations are flipped back to active with the freshly-saved content, while the translations' **SRS columns are left untouched** so review history survives a delete + re-save. No check-then-insert window (complements T18), and no schema/migration change — the fix reuses the existing unique index as the conflict target. (Case-insensitive de-duplication of `Hello` vs `hello` is tracked separately under T18/E9.)
- **Removed the composition-root `as unknown as ServiceContainer` cast and aligned `estimateCost` with its port** (Fable T03, finding C3). The double cast at the bot's composition root disabled all type-checking between adapter implementations and their port contracts, which was actively hiding a real bug: the AI port declared `estimateCost(inputTokens, outputTokens, modelId)` but the adapter implemented `estimateCost(tokens, model)`, so a call through the port passed the output-token **count** where the **model id** was expected → `findModel` returned undefined → the default price was charged silently. The adapter's `estimateCost` now matches the port signature and delegates to the existing correct `calculateCost`. Removing the cast (`const container: ServiceContainer = { … }`) surfaced several other silent port/adapter drifts, now fixed by widening the port return types to the truth the adapters already return: `UserRepository.updateNativeLang` / `updateLearningLangs` / `updateInterfaceLang` / `updateActiveMode` / `updateNotificationPrefs` (→ `Promise<UserLanguageSettings | null>`), `markOnboarded` (→ `Promise<User>`), and `VocabularyRepository.updateTranslation` (→ `Promise<VocabularyTranslation>`). The container is now compiler-verified to satisfy every port, so future drift fails the build instead of being masked.
- **Hardened the out-of-set "add & translate" flow** (Fable T02, finding B9) — closing three defects in the committed out-of-set diff. (1) **Localization:** the callback's "session expired" and "maximum languages" alerts were hardcoded English despite the flow otherwise being fully localized; they now resolve through `t()` (new `staleSession` key added to all 11 locales; the limit alert reuses `maxLangsReached`). (2) **Error separation:** *any* failure of `updateLearningLangs` (including a DB outage) was reported to the user as "you've reached the maximum number of languages". The language limit is now checked explicitly **before** the write (showing `maxLangsReached` without touching the DB), and a genuine write failure surfaces the generic `translationError` instead — a DB fault is no longer masked as a limit. (3) **Single-slot race:** `pendingOutOfSet` held one word in a single session slot, so two consecutive out-of-set prompts (e.g. a Spanish word then a Portuguese one) could add the language from the tapped button but translate the *other* word. It is now a map keyed by the prompt's Telegram message id (mirroring `translationMap`), so each button carries its own word; a used or drifted button resolves only to its own entry and its keyboard is retired (`editMessageReplyMarkup`) after selection. Also registered the `tr:oos` prefix in the `callbacks/contracts.ts` restart-safety registry (session-backed, keyed by message id).
- **Mentor mode no longer loses its history on every reply, and a single bad field no longer wipes the whole bot session** (Fable T01, findings C1/B1). The session validator's `VALID_MODES` set omitted `"mentor"` while `UserMode` declared it, so after `/mentor` each subsequent update failed `isValidSessionData` → "Resetting corrupt bot session" → the entire session (mentor history, `translationMap`, all pending state) was deleted; routing only survived because auth middleware re-hydrated the mode from the DB. Fixed at the root by introducing a single source-of-truth `USER_MODES` array in `apps/bot/src/types.ts` from which both the `UserMode` union **and** every runtime `VALID_MODES` set (session-storage and the previously-drifting copy in `middlewares/auth.ts`) are now derived — a mode can no longer be added to the type without being accepted by validation (enforced by an exhaustiveness test over `USER_MODES`). Session reads are now **non-destructive**: an invalid/unknown `activeMode` is repaired in place (defaulted, and the repair persisted) while `translationMap`, mentor history and pending state are preserved; a full delete happens only for genuinely unrecoverable (non-object) payloads. (Fable T01.)
- **Out-of-set languages are now consistently offered "add and translate" instead of slipping through** (Phase 1 of the language-guard fix). Investigating a 2026-07-03 report — the bot correctly blocked Spanish ("add this language") but silently translated Kazakh `Керемет мырзалар` and Slovak `Prečo` — surfaced that the out-of-set block was bypassable: the AI clarification could offer a **not-studied language as a tappable source** (`tr:clarify:option:` / `tr:clarify:lang:`) and translate it with no check that the language was in the user's set (`resolveTargetsForClarifiedSource`). Both the main detection guard and the clarify-callback source-selection now route a supported-but-not-studied source through a single **add-and-translate** prompt (`showAddLanguagePrompt`): `[➕ Add <lang> & translate]` / `[➡️ Translate once]` / `[Cancel]` (`tr:oos:*` callbacks). "Add" appends the language to the learning set (`userRepository.updateLearningLangs`) and translates; "once" translates without persisting. Gating uses the new `isSupportedLanguage()` registry predicate (the 46-language study registry) — **not** the i18n `isSupported` (11 UI locales) — so an unsupported detected language still gets the plain informational block (it can't be added). New i18n keys `outOfSetPrompt`, `outOfSetAddButton`, `outOfSetTranslateOnce` across all 11 locales. Also added a **word-count-independent alphabet-exclusion signal** (`detectOutOfSetByAlphabet`): when the input carries letters that no studied-language alphabet can produce and exactly one supported language can (ñ→es, ß→de, ğ→tr, ә→kk), it flags that language on the first pass — before, this was only caught for single Latin words via the dictionary sweep or for 3+ words via franc, so a confident mis-coercion slipped through. It is conservative (a diacritic shared by several languages never fires, protecting loanwords like "naïve"/"café"). (Follow-ups: multi-word/Cyrillic dictionary sweep for same-alphabet cases like `Керемет мырзалар`/`Казакша`, and restricting the AI clarification to in-set source options.)
- Language detection no longer misidentifies single foreign words as the user's sole Latin-script language (e.g. Czech "Strohá" was detected as English for a ru+en user, because being the only Latin candidate granted 0.9 confidence to any Latin text). Detection now follows lingua-style negative evidence: per-language alphabets (`packages/core/src/modules/language-detect/alphabets.ts`) veto candidates whose alphabet can't produce the input ("á" rules out English), the 0.9 "unique script candidate" score is kept only for near-1:1 scripts (hangul/kana/greek/devanagari/arabic/CJK) or when the alphabet check passes, and alphabet exclusion also narrows shared-script candidate sets ("привіт" now resolves to Ukrainian since "і" excludes Russian). A new **dictionary sweep** (`createWordLanguageSweep` over `word_context` across all supported languages) verifies heuristic-only single-word detections and detects out-of-set languages for single words — the existing `detectOutOfSetLanguage` only covered ≥3-word input — replying "🚫 {language} isn't in your selected languages" instead of mistranslating. The AI fallback may now answer with a language outside the candidate set (`AIStrategy.detectOpen`), feeding the same out-of-set reply. New telemetry events `detected`/`out_of_set` in `language_detection_events` build a golden regression set from real traffic.

Detection is a closed-set classifier (it only returns one of the user's configured languages), so e.g. a German phrase from a user with ru/en/cs/kk was coerced to the nearest candidate (English) and translated wrongly. Added a conservative out-of-set check (`detectOutOfSetLanguage`, unconstrained `francAll` over ≥3-word input) that detects the real language and replies "🚫 {language} isn't in your selected languages" instead of translating. Also fixed two Kazakh detection gaps: `kk` was missing from `ISO1_TO_ISO3` (franc could never see Kazakh) and from the Cyrillic script list (Cyrillic Kazakh never resolved by script). New i18n key `languageNotSelected` across all locales.
