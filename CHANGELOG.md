## [Unreleased]

### Added

- **Telemetry retention + timezone-aware timestamps** (Fable T25, findings E5/E6). None of the append-only telemetry/log tables (`dictionary_lookup_logs`, `translation_requests` + junction, `translation_request_timings`, `ai_request_latencies`, `language_detection_events`, `notification_history`, `word_review_log`, `bot_sessions`) had any retention horizon, so they grew forever, and every `timestamp` column was `without time zone` — correct only while Postgres and Node both ran in UTC. **Timezone:** all 42 `timestamp` columns are now `timestamp with time zone` (`{ withTimezone: true }`); migration `0043_purple_viper.sql` is a pure `ALTER COLUMN … SET DATA TYPE timestamp with time zone` type change (no `USING` clause, no data shift — safe because the dev/CI session is UTC). **Retention:** new `runTelemetryRetention(retentionDays = 90)` in `@polyglot/adapter-db` deletes rows older than a UTC-instant cutoff (`Date.now()`-derived, so the horizon is independent of the container/process timezone) from every telemetry table, including the PII-bearing text columns (`translation_requests.original`, `dictionary_lookup_logs.lookup_input`); `translation_request_target_langs` is cleaned via `ON DELETE CASCADE`. It runs as a periodic DELETE (not partitioning) because the schema is drizzle-kit-driven and hand-edited migrations / raw SQL are forbidden. It is wired as a **single in-process daily cron** (`apps/bot/src/retention.wiring.ts`, `15 3 * * *` UTC, started from `apps/bot/src/index.ts`, stopped on graceful shutdown), mirroring the notification scheduler — there is no external app cron (the release-announcement CLI is a one-shot `docker compose run`). **Rate-limit / dashboard (criterion 2):** the admin per-day dashboard now reads a new **compact `user_daily_request_counts`** counter (PK `user_id`+`day`, `udrc_day_idx` on `day`), upserted inside the request-logging transaction with a UTC `day` bucket, instead of `GROUP BY`-ing the ever-growing ledger. The **live rate-limit read is deliberately left as-is** (`getUserCreditsInWindow` summing `credit_cost` over `translation_requests` for a rolling daily window): that query is index-bounded to today's rows and now retention-bounded to 90 days, so it never scans an unboundedly-growing table — moving `credit_cost` into the counter would destabilize paid-usage gating for no real benefit. See `@docs/fable/T25-telemetry-retention-timezone.md`.
- **Bot readiness endpoint + provisioned Grafana alerts** (Fable T12, findings C4/F1). `/healthz` always returned `{status:"ok"}` regardless of whether long-polling was alive or the DB reachable, and Grafana had no alert rules — so the silent "429 freeze" incident would go unnoticed again. Added a separate **`/readyz`** on the bot's metrics server (`apps/bot/src/health.ts`) that returns **503** when long-polling looks stuck (no update processed within `READINESS_MAX_STALENESS_MS`, default 10m — tracked via a heartbeat in the update-metrics middleware) or the database ping fails (new `pingDatabase()` in `@polyglot/adapter-db`); `/healthz` stays a pure liveness signal so a quiet period never triggers a container restart. Added three **provisioned Grafana alert rules** (`deploy/monitoring/grafana/provisioning/alerting/`): bot target down (`up{job="bot"}==0`), no Telegram updates for 10m (long-polling stuck), and elevated translation error rate (`rate(bot_translations_total{status="error"})`), all routed to a Telegram contact point configured via `GRAFANA_ALERT_TELEGRAM_BOTTOKEN`/`GRAFANA_ALERT_TELEGRAM_CHATID` (Grafana-managed alerting — no external Alertmanager). `/readyz` is the foundation for the T13 deploy health gate.
- **Unrecognized-word guard** (Task 70) — stops the bot fabricating a confident card for a word that does not exist. Motivated by the "stroha" incident (a diacritic-stripped typo for Czech "strohá") where a preflight false-"proceed" led to a fully invented dictionary card. As defense-in-depth behind the preflight, the **main translation call** now also assesses whether the source headword is a real, correctly-spelled word/expression in the source language (new metadata fields `sourceWordRecognized` / `suggestedCorrection` — no extra AI call; word/phrase inputs only, opt-in via `assessSourceExistence`, off for batch/topic/video flows). An unrecognized headword yields a distinct **"unrecognized word"** clarification (reason `unrecognized_word`) offering any confident correction as a button plus "➡️ Translate as written" (reuses the Task 69 confirmation UI). Only after the user overrides is the word translated as written — the card then carries a caveat line ("⚠️ Not found in standard dictionaries — translated literally") and the saved entry is flagged **`unverified`** (new column on `vocabulary_entries`, migration `0041`). Unverified entries are **excluded from daily notifications and SRS word suggestions** (the notification dictionary picker now skips them). New telemetry counter `bot_unrecognized_word_total{outcome}` (`correction_offered` / `translated_as_written` / `rejected`). New i18n keys `translationClarifyReasonUnrecognized`, `translationTranslateAsWritten`, `translationAsWrittenCaveat`, `translationNoMoreMeanings` in all 11 locales. The dead no-op language validator (a leftover after franc-min was removed) was deleted so the validation stage honestly reflects what it checks. Additionally, the **"Other meaning"** button no longer surfaces a scary error when the pipeline has nothing new to offer (or fails) — it restores the card and shows "ℹ️ No other meanings available." instead. See `@docs/tasks/70-unrecognized-word-guard.md`.
- **Input typo & error detection in translate mode** (Task 69). The existing AI preflight now also catches typos and broken input — no extra AI call, no local spell-checker. A minor, unambiguous typo is fixed silently (new preflight outcome `proceed_with_correction`): the pipeline translates the corrected text and the reply is annotated with "✏️ Fixed: *original* → *corrected* — {why}" (the corrected form is what gets saved to the dictionary, so no typo cards enter SRS). Severe or ambiguous typos still use `confirm_typo_suggestion` with "✅ Yes, I meant …" / "➡️ Translate as written" buttons — choosing "translate as written" re-runs verbatim (saving the exact input) and never re-asks. Broken sentences are translated as their reconstructed meaning with the corrected sentence and a short error note; a confirm dialog appears only when the meaning cannot be reconstructed. The severity boundary and the correction/error `explanation` (now written in the user's `nativeLang`, length-capped) live in the preflight prompt. Language-clarification keyboards now render **flag + code** buttons (e.g. `🇬🇧 EN`) built on our side from `langCode` in rows of up to 4, with the "Add context" button on its own row and a hint line explaining the icons — model option labels no longer carry language names. New telemetry counter `bot_input_correction_total{outcome, input_type}` (`auto_corrected` / `confirm_shown` / `confirmed` / `translate_as_written`). After the language/mistype confirmation flow the preflight runs with a no-correction flag (`skipInputCorrection`) so the same word is never re-questioned. **The typo check is not gated on language detection**: confident detection does not mean correct spelling ("stroha" was confidently detected as Czech and translated verbatim although only "strohá" exists). The context-enrichment layer now reports whether the input exists in the source-language dictionary (`dictionaryHit`), and a dictionary miss forces the AI preflight to run even at high detection confidence — for every language; the preflight prompt carries the dictionary-miss signal plus an explicit rule that missing/wrong diacritics (stroha → strohá, uber → über, cancion → canción) are minor typos to restore. Sentences (never dictionary-checkable) now always get the preflight error check in translate mode. New i18n keys `correctionNotice`, `sentenceErrorNotice`, `translationClarifyLanguageHint` in all 11 locales. See `@docs/tasks/69-input-typo-validation.md`.
- Bot latency observability in Prometheus/Grafana, closing the blind spot found while investigating the 2026-07-02 delayed-answer report. New `update-metrics` middleware (registered before session middleware) records `bot_update_handling_duration_seconds{update_type}` for every update, `bot_update_delivery_lag_seconds` from the Telegram message timestamp (long-polling delivery delay), and logs a `Slow update handling` warning to Loki when handling or delivery exceeds 3 s. Postgres-backed session storage now records `bot_session_storage_duration_seconds{op=read|write|delete}` — a direct view of Neon round-trip latency (including autosuspend wake-ups) on every update. Three new P95/P50 panels on the Grafana **Polyglot Bot** dashboard: Update Handling Duration, Update Delivery Lag, Session Storage / Neon Latency.
- Persistent loading feedback for long bot operations. On-demand card sections that previously ran with **no waiting UX and swallowed errors silently** — "Other meaning", grammar breakdown, etymology, per-language grammar detail — now swap the card's buttons for an inert "⏳ Loading…" button while generating (the callback is answered only at the end, so Telegram's button spinner also stays visible), restore the card and show an explanatory alert on failure. Notification reveal/learned callbacks get the same loading button (their user-language and entry lookups now run in parallel, saving one Neon round-trip). Translate and mentor text flows show a "typing…" chat action during the silent pre-phase before their loader message appears. New i18n keys `loading` and `loadingTimeout` across all 11 locales.
- **Real cancellation of hung AI requests** at the adapter boundary (`packages/adapters/ai/src/index.ts`). Every `generateObject` / `generateText` / `generateChat` call now runs under an `AbortController` whose signal is passed to the Vercel AI SDK, so a single wall-clock budget bounds the whole call **including the SDK's internal retries**. When the budget elapses the in-flight HTTP request is genuinely aborted — freeing the socket and the OpenRouter concurrency slot instead of leaving it hanging in the background — and the adapter throws a typed `AITimeoutError` (`@polyglot/core`), logged as a failed request. This closes the gap left by the bot's `withTimeout` guard, which only abandoned the `await` (its own doc: "the underlying work is not cancelled"). The budget is **admin-managed** — a new `requestTimeoutMs` field on the AI Defaults settings (stored in the DB `system_settings` `ai.defaults` row, editable in the admin panel's **AI Defaults** tab, `1000–20000 ms`, default **15 s**). The adapter reads it through an injected provider (`setAIRequestTimeoutProvider`, wired at the bot composition root over the cached `SettingsService` — same dependency-injection pattern as the metric sink), so changing it in the admin panel takes effect without a redeploy, and it falls back to 15 s if unset/invalid. It is deliberately kept below the bot's 20 s loader guard so the adapter cancels first and the user still sees the friendly "taking longer" fallback. A new `isUserFacingTimeout` predicate (`apps/bot/src/utils/long-op.ts`) maps both `AITimeoutError` and the op-level `OperationTimeoutError` to the "⌛ This is taking longer than expected. Please try again." message across every long-op catch site (translate, alt-meaning, grammar detail, mentor, dictionary, notification callbacks). Directly addresses the 2026-07-01 freeze, where a rate-limited `:free` model's un-aborted retries held resources for 40–110 s.
- Timeout guard (20 s, `withTimeout` in `apps/bot/src/utils/long-op.ts`) around every user-facing long operation (translation, alt-meaning, grammar, etymology, grammar detail, mentor chat, dictionary-entry translation, notification callbacks): instead of an endless loader, the user gets "⌛ This is taking longer than expected. Please try again." — motivated by the 2026-07-01 incident where free-tier model retries ran 40–110 s.

### Changed

- **Composable infra env schema — apps without Telegram no longer need `BOT_TOKEN`** (Fable T24, finding A18 — first slice of the multichannel refactor). `@polyglot/infra`'s `loadConfig` hardcoded a single env schema that unconditionally required `BOT_TOKEN`, and it called `process.exit(1)` from library code on invalid env. The schema is now composable: `baseEnvSchema` (shared, no channel secrets) + a `telegramEnvSchema` extension carrying `BOT_TOKEN`, combined into `botEnvSchema`. `loadConfig<T>(schema?)` takes the schema an app needs (defaulting to base) and **throws a typed `ConfigError`** (carrying zod's treeified issues) instead of exiting — the `process.exit` now lives only at the application entry points (`apps/bot/src/index.ts`, `release-announcement.cli.ts`), which pass `botEnvSchema` and map `ConfigError` to a logged exit. A channel-less app (admin API, workers) can now load its config from base without a Telegram token. `Env` is kept as a backwards-compatible alias for `botEnvSchema`. The remaining T24 work (neutral `userId` + `identities` table, `SendFn(userId)`, `channelHint` in prompts) is a follow-up. See `@docs/fable/T24-multichannel-identities.md`.
- **`translate()` step pipeline + domain/presentation split** (Fable T23, findings A12/A13). `translate()` in `packages/core/src/modules/translation/translation.service.ts` was a ~350-line orchestrator running preflight, typo correction, generation+retries, validation, repair, judge and risk-routing in one body, and `TranslateInput` had grown three flat task-flags (`dictionaryHit`, `skipInputCorrection`, `assessSourceExistence`) so every new task edited the same place — a budding god-object. **(A12) Pipeline:** the body is now a thin orchestrator over an explicit, ordered `TRANSLATION_PIPELINE` of steps (`structuralPreflight → aiPreflight → generate → unrecognizedGuard → validateAndRepair → judge → finalize`) threading one `PipelineContext`; each step either `continue`s (context updated) or `exit`s with a `TranslationDecision`, so the early-exit paths (typo/clarification/unrecognized-word/judge) are modeled as explicit step outcomes rather than scattered `return`s. Adding a phase is adding a step + array entry (OCP) — no existing step body changes. Behavior is identical (the existing translation.service suite is unchanged bar the type/structure updates below). **(A13) Domain/presentation split:** core no longer returns localized UI strings from `translate()`. `buildUnrecognizedAmbiguity` previously called `t()`/`getLanguageName` to build the "unrecognized word" clarification message and the "translate as written" button label; it now returns a **structured** `TranslationAmbiguity` — `reason` + `params` (`word`, source-language `lang` CODE) and an option with no label — and the **bot** localizes it (`clarificationReasonText` reads `params`, the keyboard derives the "translate as written" label from `kind`). The structural preflight (mixed-script / ambiguous numeric date) likewise dropped its hardcoded English `message`, keeping only the structured reason + option data. `TranslationAmbiguity.message` and `TranslationAmbiguityOption.label` are now optional; AI-preflight explanations (model output already in the user's language) still flow through `message`. This removes core's i18n import from the translate path — the multichannel prerequisite for T24. **(A13) Policy object:** the three flat flags are grouped into `TranslateInput.correctionPolicy` (`TranslationCorrectionPolicy`); the context-enrichment layer fills `correctionPolicy.dictionaryHit`, the bot passes `assessSourceExistence`/`skipInputCorrection` there, and an absent policy behaves exactly as before. New spec-first tests: structured unrecognized-word + date reasons in core, and a bot test proving the clarification arrives as a structure the channel renders via `t()`. See `@docs/fable/T23-translate-pipeline.md`.
- **admin-api service layer + shared contracts package** (Fable T27, findings D3/D4). The admin panel and admin-api each carried their own copy of the request zod-schemas (`apps/admin/src/lib/validation.ts` vs inline schemas in every route file), so the two drifted; controllers also wrote raw Drizzle in handlers (`users.ts`, `stats.ts`) and duplicated settings defaults (`ai-defaults.ts`/`dictionary.ts` vs the core `SettingsService` fallbacks). **Contracts (D4):** new `@polyglot/admin-contracts` package holds the shared zod schemas + `zodErrorMessage` as the **single source** consumed by both the frontend forms (`.vue`) and the backend routes — `validation.ts` is deleted and every inline route schema removed; numeric fields use `z.coerce.number()` so one schema validates both HTML-form strings and JSON numbers. **Service layer (D3):** AI-model business invariants (can't delete the default model, can't set a disabled model default — the T11/D2 :free-freeze guards) moved out of the route into `apps/admin-api/src/services/ai-model.service.ts`, throwing an `HttpError` the global handler maps to a clean 4xx; the raw Drizzle in `users.ts` (paginated list + plan update) and `stats.ts` (dashboard overview) moved into repository methods (`userRepository.listAdmin`/`updatePlan`, new `statsRepository.getOverview`), so **no handler touches Drizzle directly** (raw queries live only in `packages/adapters/db`). **CRUD factory:** new `registerCrudRoutes(app, options)` + shared `paginationQuerySchema` (`crud-factory.ts`) wire list/create/update/delete with consistent query validation & clamping; **presets** and **rate-limit plans** are migrated onto it, and the users list reuses the shared pagination schema. **Defaults dedupe:** `ai-defaults`/`dictionary`/`srs`/`notifications` now return the core `FALLBACK_*` constants instead of local literals. Reported-issues stays bespoke (its status-enum body is tied to the DB `IssueStatus` type and its update is a non-CRUD `PUT /:id/status`); the rate-limit default-plan guard remains in the repository transaction (it reassigns affected users atomically) with its failure surfaced as a 400. - **One language registry, not two** (Fable T21, finding A3 — final slice of the code/DB dual-source epic). Language metadata lived in two parallel in-memory stores with byte-identical normalization logic: core's `i18n/language-registry.ts` and adapter-db's `language-cache.ts`. The bot loaded the `languages` table once, then stored it twice (`loadLanguageCache` filled the adapter map, then `initLanguageRegistry` filled the core map from it) and every `getLangName`/`normalizeToIso1`/`getLangDisplay` existed in both. The core registry is now the **single** in-memory source of truth: `initLanguageRegistry` normalizes each row to the canonical `CachedLanguage` shape (filling id/nativeName/flag/localizedNames defaults), and adapter-db's `language-cache` is reduced to a thin **loader + delegator** — `loadLanguageCache` reads the DB straight into the registry, and every getter forwards to it (no second map, no duplicated logic). The bot startup drops its redundant manual `initLanguageRegistry` call. Public function surface (`getLang`, `getAllLangs`, `getSupportedLangs`, `getLangDisplay`, …) is unchanged, so call sites and the `LanguageCachePort` contract are untouched. This completes T21 — plan tariffs, model prices, generation defaults, judge model, and language metadata all now have a single source.

### Fixed

- **Close check-then-insert races and stop card regen wiping SRS progress** (Fable T18, findings E4/E8/E9). Several `select → insert` patterns had no unique-constraint backstop: (E4) a brand-new user's first messages/callbacks arrive concurrently, so two `findByTelegramId → create` calls could collide on the unique `telegram_id` and drop the first interaction — `userRepository.create` is now idempotent (`onConflictDoNothing` on `telegram_id` + re-select). (E8) `getOrCreateDefault` could insert a second default dictionary under a race — it now upserts via `onConflictDoNothing` on the unique `(user_id, name)` index + re-select; and `updateAllTranslations` used to **delete + re-insert** every translation on a full card regen, resetting each row's SRS schedule — it now **upserts** keyed on `(entry_id, target_lang_id)`, updating only content columns and leaving every `srs_*` column untouched (stale-language rows are pruned), so regenerating a card no longer wipes review progress. (E9) `logTranslationRequest` did three writes without a transaction — the request row and its target-language rows are now written atomically so a mid-write failure can't corrupt credit accounting. (Case-insensitive dictionary dedup and fully-atomic paid-tier rate limiting remain follow-ups needing a coordinated `original`/`word` normalization design shared with T04/T17.)
- **Index the `word_context` hot path — no more seq scan on every translation** (Fable T17, finding E2). Both the translation preflight (`context-lookup.ts`) and the single-word language sweep looked words up with `ILIKE(word, …)` (which a btree index can't serve) plus `arrayContains(forms, [word])` (which needs a GIN index — none existed), so on the kaikki dictionary dumps (hundreds of thousands to millions of rows) every message triggered a full table scan. The two hot lookups now use a case-insensitive **exact** match, `lower(word) = lower($1)`, backed by a new functional index `word_context_lower_word_idx` on `lower(word)`, and `arrayContains(forms, …)` is backed by a new **GIN** index `word_context_forms_gin_idx` (migration `0042`). Lowercasing is applied symmetrically on both sides so lookup results are unchanged; the admin partial-substring `search()` keeps its `ILIKE %…%`. (Full NFC write-side normalization, shared with the dictionary-dedup work, is a follow-up.)
- **Safe global bot error handler with a user reply** (Fable T15, finding B3). The old `bot.catch` only logged, and it read `ctx.session.activeMode` unconditionally — if a failure happened **before** the session middleware ran (in `update-metrics` or `sequentialize`), accessing `ctx.session` threw *inside the error handler*, producing an unhandled rejection in the runner; meanwhile the user was left staring at a frozen "Translating…". The handler (extracted to `apps/bot/src/bot-error-handler.ts`) now wraps its whole body in try/catch so it can never throw, reads `ctx.session` defensively, sends a **best-effort reply** (`genericError`, localized from the user's Telegram client language — no DB lookup in the error path) so no loader hangs, answers a pending callback to stop the button spinner, and classifies the cause as `telegram` (`GrammyError`) / `network` (`HttpError`) / `application` for the logs (aligned with T14). New i18n key `genericError` in all 11 locales.
- **Guard the admin AI-model controls against removing the model the bot depends on** (Fable T11, finding D2). `DELETE /ai-models/:id` would delete *any* model, including the current default, and `set-default` never checked that the target was enabled — either way the bot could be left pointing at a model it cannot call, falling back to a hardcoded id that may be unavailable (the same failure class as the `:free` 429 freeze). Deleting the current default now returns **409** ("Set another model as default first"), and setting a **disabled** model as default now returns **409** ("Enable it first"); a missing model still returns 404. The `logAiModelChange` audit log is unchanged. (A configurable fallback chain is tracked under T30/B15; the systemic move of the model/price source into the DB is T21.)

### Security

- **Unified AI credit metering across all paid flows** (Fable T16, findings S1/S5 — economic DoS on the owner's OpenRouter key). The daily credit quota was enforced **only** in the translate flow, so mentor chat, dictionary re-translate, and video phrase extraction ran unmetered — a free user could hold an endless mentor conversation (throttled only by `sequentialize`) or feed long YouTube transcripts, burning money on the owner's key (and amplifying the prompt-injection blast radius). Added a single metering point, `apps/bot/src/utils/ai-quota.ts` (`ensureAiQuota` + `recordAiUsage`), used by **every** paid AI call — translate, mentor, dictionary-translate, and video — replacing the translate-only `ensureTranslationQuota`. Each call type has a weight (`translate` 1, `mentor` 2, `dictionaryTranslate` 1, `video` 5) so heavier calls cost proportionally more, and all consumption is recorded in the shared credit ledger (tagged `[mentor]`/`[video]`/…). An exhausted quota now refuses the call in every flow with the same rate-limit notice instead of a free AI call. Tests cover the weights, the exact-limit boundary, quota exhaustion, and mentor refusing/​billing correctly.
- **RBAC + one unified auth hook — admin roles are now enforced** (Fable T07, finding S8). The JWT already carried a `role` (`superadmin`/`admin`) but **no route ever checked it**, so any active admin could delete AI models, delete tariff plans, or change users' subscription plans; meanwhile the `authenticate` decorator was dead code and all 11 route groups copy-pasted their own `onRequest` `jwtVerify` hook. Consolidated auth into a single hook in `apps/admin-api/src/plugins/auth.ts`: it verifies the JWT (and runs the T06 `isActive` revocation check) and populates `request.adminUser` for every non-public route in one place — the 11 duplicated hooks and the dead `authenticate` decorator are gone. Added a `requireRole("superadmin")` preHandler now applied to the destructive/privileged mutations — AI-model create/update/delete + set-default, tariff-plan upsert/delete, and user plan/audience-group changes — so an insufficient role gets **403**. Public routes (`/healthz`, `/api/auth/login`) and CORS preflight remain open.
- **Runtime revocation of admin access — deactivated admins lose access immediately, not in 24h** (Fable T06, finding S4). `isActive` was checked **only at login**; every other route and `/me` did a bare `jwtVerify`, so a blocked or deleted admin kept full access until their 24h token expired (no blacklist, no `tokenVersion`, no secret rotation). Now every `request.jwtVerify()` — across all 11 route groups — runs through `@fastify/jwt`'s `trusted` hook, which re-checks the admin's current `isActive` against the DB and rejects a deactivated/deleted admin with **401**. To avoid a DB read on every request, the check is backed by a short in-memory cache (`ADMIN_ACTIVE_CACHE_TTL_MS`, 30s) keyed by admin id, so a deactivated admin loses access within the TTL rather than at token expiry, and a burst of requests hits the DB at most once per TTL. Implemented at a single point in `apps/admin-api/src/plugins/auth.ts` (no per-route changes), which also sets up the unified auth hook that T07 builds on for RBAC.
- **Global error handler + query-parameter validation on the admin API** (Fable T08, findings S9/D5). Admin routes read pagination/window params straight off `request.query` with `Number.parseInt` and no bounds, and route-level `zod.parse()` failures had no error handler — so `?limit=abc` surfaced as a **500 leaking the ZodError internals** (schema shape, field paths) and `?limit=100000` would try to dump the whole `users` table. A new global Fastify error handler (`apps/admin-api/src/error-handler.ts`, wired in `index.ts`) maps any `ZodError` to a clean **400** with a generic body (`{ error: "Invalid request parameters" }` — no schema/paths), logs and hides 5xx behind a generic `Internal Server Error`, and lets already-safe 4xx (auth 401, rate-limit 429) pass through. `GET /api/users` and the `/api/stats/*` timing endpoints now validate their query via zod: non-numeric input is rejected (400), and `page`/`limit`/`days` are **clamped** to sane ranges (`limit ≤ 100`, `days` 1–90) instead of being trusted. The `/users` list also now computes `total` with the **same** search filter as the page selection (it previously counted the whole table), so paginated search results stay consistent. Separately, the `/stats` **"active today"** count now reflects real activity — it counts `user_language_settings.last_interaction_at` within 24h instead of `users.created_at` (which only ever counted same-day *registrations*).
- **Redact PII from logs shipped to third parties** (Fable T10, finding S7). The core pino logger had no `redact` config, so user message fragments and identifiers reached Betterstack/Loki at `info`+ — including a mentor-chat **error** log that shipped a 50-char slice of the user's message. Configured pino `redact` for the PII/secret paths `text`, `username`, and `password` (top-level and one level nested) → `[Redacted]`. The mentor error now logs `textLength` (a length category) instead of raw text; the two debug-only routing logs use `textPreview` (visible for local debugging, never shipped because prod runs at `info`); and the bot-startup log's own handle was renamed `username` → `botUsername` so it stays visible (it is not user PII). Identifiers like `userId`/`telegramId` are kept for diagnostics. (Email in the T05 failed-login log is intentionally not redacted — it is needed for brute-force alerting.)
- **Closed the anonymous leak of internal reports** (Fable T09, finding S3). `apps/admin/public/reports/` — the full database schema, architecture map, observability report, and the ~1950-scenario test catalog (file paths + behavior descriptions) — was served by Astro as **unauthenticated static assets** and proxied to the internet, handing any anonymous visitor a complete map of the system. ### Fixed

- **Re-saving a word you previously deleted no longer crashes** (Fable T04, findings C2/E1). Deleting a word from a notification is a soft-delete (the row stays with `is_active = false`), but the duplicate check (`findByOriginalAndSource`) only looks at active rows, so a re-save found nothing and inserted — colliding with the `(user_id, original, source_lang_id)` unique index and throwing an unhandled `23505`. `vocabularyRepository.create` now **reactivates** the existing row via a race-safe `ON CONFLICT DO UPDATE` (on the entry's unique key and each translation's `(entry_id, target_lang_id)` key): the entry and its translations are flipped back to active with the freshly-saved content, while the translations' **SRS columns are left untouched** so review history survives a delete + re-save. No check-then-insert window (complements T18), and no schema/migration change — the fix reuses the existing unique index as the conflict target. (Case-insensitive de-duplication of `Hello` vs `hello` is tracked separately under T18/E9.)
- **Removed the composition-root `as unknown as ServiceContainer` cast and aligned `estimateCost` with its port** (Fable T03, finding C3). The double cast at the bot's composition root disabled all type-checking between adapter implementations and their port contracts, which was actively hiding a real bug: the AI port declared `estimateCost(inputTokens, outputTokens, modelId)` but the adapter implemented `estimateCost(tokens, model)`, so a call through the port passed the output-token **count** where the **model id** was expected → `findModel` returned undefined → the default price was charged silently. The adapter's `estimateCost` now matches the port signature and delegates to the existing correct `calculateCost`. Removing the cast (`const container: ServiceContainer = { … }`) surfaced several other silent port/adapter drifts, now fixed by widening the port return types to the truth the adapters already return: `UserRepository.updateNativeLang` / `updateLearningLangs` / `updateInterfaceLang` / `updateActiveMode` / `updateNotificationPrefs` (→ `Promise<UserLanguageSettings | null>`), `markOnboarded` (→ `Promise<User>`), and `VocabularyRepository.updateTranslation` (→ `Promise<VocabularyTranslation>`). The container is now compiler-verified to satisfy every port, so future drift fails the build instead of being masked.
- **Hardened the out-of-set "add & translate" flow** (Fable T02, finding B9) — closing three defects in the committed out-of-set diff. (1) **Localization:** the callback's "session expired" and "maximum languages" alerts were hardcoded English despite the flow otherwise being fully localized; they now resolve through `t()` (new `staleSession` key added to all 11 locales; the limit alert reuses `maxLangsReached`). (2) **Error separation:** *any* failure of `updateLearningLangs` (including a DB outage) was reported to the user as "you've reached the maximum number of languages". The language limit is now checked explicitly **before** the write (showing `maxLangsReached` without touching the DB), and a genuine write failure surfaces the generic `translationError` instead — a DB fault is no longer masked as a limit. (3) **Single-slot race:** `pendingOutOfSet` held one word in a single session slot, so two consecutive out-of-set prompts (e.g. a Spanish word then a Portuguese one) could add the language from the tapped button but translate the *other* word. It is now a map keyed by the prompt's Telegram message id (mirroring `translationMap`), so each button carries its own word; a used or drifted button resolves only to its own entry and its keyboard is retired (`editMessageReplyMarkup`) after selection. Also registered the `tr:oos` prefix in the `callbacks/contracts.ts` restart-safety registry (session-backed, keyed by message id).
- **Mentor mode no longer loses its history on every reply, and a single bad field no longer wipes the whole bot session** (Fable T01, findings C1/B1). The session validator's `VALID_MODES` set omitted `"mentor"` while `UserMode` declared it, so after `/mentor` each subsequent update failed `isValidSessionData` → "Resetting corrupt bot session" → the entire session (mentor history, `translationMap`, all pending state) was deleted; routing only survived because auth middleware re-hydrated the mode from the DB. Fixed at the root by introducing a single source-of-truth `USER_MODES` array in `apps/bot/src/types.ts` from which both the `UserMode` union **and** every runtime `VALID_MODES` set (session-storage and the previously-drifting copy in `middlewares/auth.ts`) are now derived — a mode can no longer be added to the type without being accepted by validation (enforced by an exhaustiveness test over `USER_MODES`). Session reads are now **non-destructive**: an invalid/unknown `activeMode` is repaired in place (defaulted, and the repair persisted) while `translationMap`, mentor history and pending state are preserved; a full delete happens only for genuinely unrecoverable (non-object) payloads. (Fable T01.)
- **Out-of-set languages are now consistently offered "add and translate" instead of slipping through** (Phase 1 of the language-guard fix). Investigating a 2026-07-03 report — the bot correctly blocked Spanish ("add this language") but silently translated Kazakh `Керемет мырзалар` and Slovak `Prečo` — surfaced that the out-of-set block was bypassable: the AI clarification could offer a **not-studied language as a tappable source** (`tr:clarify:option:` / `tr:clarify:lang:`) and translate it with no check that the language was in the user's set (`resolveTargetsForClarifiedSource`). Both the main detection guard and the clarify-callback source-selection now route a supported-but-not-studied source through a single **add-and-translate** prompt (`showAddLanguagePrompt`): `[➕ Add <lang> & translate]` / `[➡️ Translate once]` / `[Cancel]` (`tr:oos:*` callbacks). "Add" appends the language to the learning set (`userRepository.updateLearningLangs`) and translates; "once" translates without persisting. Gating uses the new `isSupportedLanguage()` registry predicate (the 46-language study registry) — **not** the i18n `isSupported` (11 UI locales) — so an unsupported detected language still gets the plain informational block (it can't be added). New i18n keys `outOfSetPrompt`, `outOfSetAddButton`, `outOfSetTranslateOnce` across all 11 locales. Also added a **word-count-independent alphabet-exclusion signal** (`detectOutOfSetByAlphabet`): when the input carries letters that no studied-language alphabet can produce and exactly one supported language can (ñ→es, ß→de, ğ→tr, ә→kk), it flags that language on the first pass — before, this was only caught for single Latin words via the dictionary sweep or for 3+ words via franc, so a confident mis-coercion slipped through. It is conservative (a diacritic shared by several languages never fires, protecting loanwords like "naïve"/"café"). (Follow-ups: multi-word/Cyrillic dictionary sweep for same-alphabet cases like `Керемет мырзалар`/`Казакша`, and restricting the AI clarification to in-set source options.)
- Language detection no longer misidentifies single foreign words as the user's sole Latin-script language (e.g. Czech "Strohá" was detected as English for a ru+en user, because being the only Latin candidate granted 0.9 confidence to any Latin text). Detection now follows lingua-style negative evidence: per-language alphabets (`packages/core/src/modules/language-detect/alphabets.ts`) veto candidates whose alphabet can't produce the input ("á" rules out English), the 0.9 "unique script candidate" score is kept only for near-1:1 scripts (hangul/kana/greek/devanagari/arabic/CJK) or when the alphabet check passes, and alphabet exclusion also narrows shared-script candidate sets ("привіт" now resolves to Ukrainian since "і" excludes Russian). Shared diacritics (á, é) now score 0.4 instead of a decisive 0.8 — only globally unique marks (ř→cs, ł→pl, ß→de) stay strong. A new **dictionary sweep** (`createWordLanguageSweep` over `word_context` across all supported languages) verifies heuristic-only single-word detections and detects out-of-set languages for single words — the existing `detectOutOfSetLanguage` only covered ≥3-word input — replying "🚫 {language} isn't in your selected languages" instead of mistranslating. The AI fallback may now answer with a language outside the candidate set (`AIStrategy.detectOpen`), feeding the same out-of-set reply. New telemetry events `detected`/`out_of_set` in `language_detection_events` build a golden regression set from real traffic.
- Language detection no longer silently mistranslates input written in a language the user hasn't selected. Detection is a closed-set classifier (it only returns one of the user's configured languages), so e.g. a German phrase from a user with ru/en/cs/kk was coerced to the nearest candidate (English) and translated wrongly. Added a conservative out-of-set check (`detectOutOfSetLanguage`, unconstrained `francAll` over ≥3-word input) that detects the real language and replies "🚫 {language} isn't in your selected languages" instead of translating. Also fixed two Kazakh detection gaps: `kk` was missing from `ISO1_TO_ISO3` (franc could never see Kazakh) and from the Cyrillic script list (Cyrillic Kazakh never resolved by script). New i18n key `languageNotSelected` across all locales.
